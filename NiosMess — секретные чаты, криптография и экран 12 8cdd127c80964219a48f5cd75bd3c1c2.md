## 🔴 Блокеры (9)

### КРИП-1 · Почему твои сообщения через пару секунд становятся пустыми

Нашёл. Это не UI и не гонка — это архитектура. Цепочка из четырёх звеньев, каждое по отдельности выглядит безобидно.

**Звено 1.** Модель принудительно вырезает контент у любого E2EE-сообщения. `ApiMessage.fromJson`:

```dart
content: isE2ee ? '' : (json['content'] as String? ?? ''),
```

**Звено 2.** В `send()` это чинится костылём, но только в памяти:

```dart
if (isE2ee) {
  sent = sent.copyWith(content: trimmed, e2eeFileKey: e2eeFileKey);
}
```

Поэтому сразу после отправки сообщение видно. Единственная копия открытого текста — вот эта, в состоянии провайдера.

**Звено 3.** Double Ratchet устроен так, что **отправитель не может расшифровать своё же сообщение**. Ключ берётся из отправляющей цепочки (`chnKsx`), а `decrypt` умеет только принимающую (`chnKrx`). Это не баг библиотеки, это свойство схемы. Но `_decryptE2eeMessages` не различает свои и чужие сообщения:

```dart
if (!msg.isE2ee || msg.e2eeContent == null || msg.e2eeContent!.isEmpty) {
  result.add(msg);
  continue;
}
try {
  final String decrypted = await e2eeService.decryptE2EEMessage(...);
  result.add(msg.copyWith(content: decrypted));
} catch (e) {
  debugPrint('E2EE decrypt failed for msg ${msg.id}: $e');
  result.add(msg);   // content остаётся пустым
}
```

**Звено 4.** Любой повторный забор истории затирает память и кэш. `_fetch`:

```dart
final List<ApiMessage> messages = await getHistory(_chatId, pageSize: 80);
final List<ApiMessage> decrypted = await _decryptE2eeMessages(messages);
await EncryptedMessageCache.saveMessages(_chatId, decrypted);
```

Итог: сервер отдаёт твоё сообщение с `is_e2ee: true` → `content` пустой → расшифровка своего же шифротекста падает → в состояние кладётся пустое сообщение → пустое сообщение записывается в кэш поверх открытого текста. **Плейнтекст уничтожен безвозвратно.**

Пара секунд — это первый же `refresh`. Триггеров много: таймер опроса секретного чата в `chat_detail_screen`, pull-to-refresh, переподключение WebSocket, возврат приложения из фона, и `loadOlder` при листании вверх.

И то же самое объясняет мою прошлую находку ПЛАВ-1 — **с уточнением, и здесь я себя поправлю**. Я писал, что повторная расшифровка съедает ключи Double Ratchet и портит сессию. Это неверно: `DoubleRatchetService.decrypt` работает на копии (`final tmpSession = session.copy()`) и коммитит состояние только после успеха. Сессия не портится. Но открытый текст всё равно теряется и всё равно уезжает в кэш — последствие ровно то же, механизм другой.

**Что делать.** Нужна отдельная запись своего плейнтекста при отправке. Три необходимых шага:

1. Хранить открытый текст исходящего E2EE-сообщения локально — в `EncryptedMessageCache` по `messageId` (кэш уже шифрованный, это подходящее место). При склейке истории подставлять его для своих сообщений.
2. В `_decryptE2eeMessages` пропускать сообщения, где `senderId == myUserId` — расшифровать их невозможно by design, попытка только жжёт время и обнуляет текст.
3. Добавить признак «уже расшифровано». Сейчас его нельзя выставить: `ApiMessage.copyWith` использует `e2eeContent ?? this.e2eeContent`, то есть **обнулить `e2eeContent` невозможно**. Нужно либо поле `isDecrypted`, либо явный `clearE2eeContent` в `copyWith`.

Без пункта 1 переписка в секретном чате нечитаема для тебя же после любого обновления — это не деградация, это полная неработоспособность фичи.

### КРИП-2 · Пропущенные ключи сообщений не сохраняются — потеря сообщений после перезапуска

`DoubleRatchetSession.toJson()` сериализует `ratKey`, `dhsSeed`, `dhrKey`, `chnKsx`, `chnKrx`, `numSnt`, `numRcv`, `prvNum`, `keyVal`, `prvKey`, `peerStaticEd`. В списке **нет `skipKs`** — карты ключей для сообщений, пришедших не по порядку.

Сценарий: собеседник отправил сообщения 5, 6, 7; до тебя дошли 7 и 5, шестое застряло. `skipKs` держит ключ для 6. Перезапустил приложение → `_loadSession` восстановил всё, кроме `skipKs` → **сообщение 6 уже никогда не расшифруется**. Навсегда пустое.

Вторая часть той же проблемы — в `decrypt`:

```dart
final mksKey = '${header.dh}_${header.n}';
if (session.skipKs.containsKey(mksKey)) {
  final msgKey = session.skipKs.remove(mksKey)!;
  return _decryptWithKey(msgKey, headerBytes, ciphertext);
}
```

Ключ удаляется **до** того, как выяснится, успешна ли расшифровка. Если `_decryptWithKey` вернул `null` (битые байты, несовпадение AAD), ключ потерян, и повторная попытка уже невозможна. Плюс рассинхрон: `_saveSession` вызывается только при успехе, поэтому в памяти ключа нет, а на диске он остался.

Лечится: `skipKs` в `toJson`/`fromJson`; удаление ключа только после успешной расшифровки; TTL и лимит на размер карты, чтобы она не росла бесконечно.

### КРИП-3 · Инициатор записывает свой собственный Ed25519 как ключ собеседника

`ensureSecretHandshake` в `backend_chat_provider.dart`:

```dart
final String edPubB64 = await e2ee.getEdPublicKeyBase64();
await e2ee.initiateHandshake(
  chatId: _chatId,
  theirPublicKeyBase64: partnerPublicKey,
  theirEdPublicKeyBase64: edPubB64,   // это НАШ ключ
);
```

`getEdPublicKeyBase64()` возвращает **наш** Ed25519. Он уезжает в `_dr.initiateSession(peerStaticEdB64: ...)` и ложится в `session.peerStaticEd` как идентичность собеседника.

Три последствия:

1. `getSessionInfo` считает `peerFp` из `session.peerStaticEd` → в шторке верификации **«отпечаток собеседника» равен твоему собственному**. Две строки отпечатков идентичны. Пользователь сравнивает с собеседником — не совпадает никогда.
2. `verifyPeer(chatId)` пишет `_verifiedPeers[chatId] = session.peerStaticEd`, то есть **подтверждает твой же ключ** как доверенный ключ собеседника.
3. Дальше `handleHeloMessage` сравнивает `_verifiedPeers[chatId] != theirEdPublicKeyBase64` → расхождение гарантировано → **ложная тревога MITM** и статус `compromised` на легитимной сессии.

Правится только при полном хендшейке: `completeHandshake` перезаписывает `pending.peerStaticEd` настоящим ключом из HELO. Но если HELO собеседника не пришёл (он не открыл чат), состояние остаётся отравленным, а пользователь уже видит «отпечатки» и кнопку «Подтвердить».

Нужно: не принимать Ed25519 собеседника из воздуха. Либо получать его с сервера вместе с `partner_public_key`, либо оставлять `peerStaticEd` пустым до HELO и не показывать блок отпечатков, пока идентичность не подтверждена подписью.

### КРИП-4 · Тихий откат на статическое шифрование без forward secrecy

`send()`:

```dart
if (session != null) {
  e2eeContent = await e2eeService.encryptE2EEMessageDR(plaintext: e2eePlain, chatId: _chatId);
} else {
  e2eeContent = await e2eeService.encryptE2EEMessage(
    plaintext: e2eePlain, chatId: _chatId,
    theirPublicKeyBase64: chat.partnerPublicKey!,
  );
}
isE2ee = true;
```

Вторая ветка — легаси v1: один статический ECDH-секрет на всю переписку, AES-GCM, `getOrComputeSharedSecret` его кэширует. **Никакого ратчета, никакой forward secrecy**: утечка приватного ключа раскрывает всю историю переписки целиком. Это именно то свойство, ради которого Double Ratchet и существует.

У пользователя при этом в интерфейсе тот же замок и та же надпись про сквозное шифрование. Разницы между v2 и v1 UI не показывает вообще, а бейдж в шторке захардкожен как `'E2EE v1'`.

И ветка не гипотетическая: `getOrCreateSession` возвращает `null`, пока хендшейк не прошёл, а инициирует его только одна сторона (`ourPub.compareTo(partnerPublicKey) > 0`) и только в `build()` провайдера. Если собеседник ещё не открывал чат — сессии нет, и все твои сообщения уходят по слабой схеме.

Нужно: либо убрать v1 полностью и блокировать отправку до установления сессии (с честным состоянием «устанавливаем защищённое соединение»), либо явно помечать такие сообщения в UI как «ослабленное шифрование». Молча — нельзя.

### КРИП-5 · 12 слов не совпадают у двух сторон, а сравниваемый хеш считается не от того ключа

Две независимые ошибки в одном механизме.

**Первая — рассинхрон сразу после хендшейка.** `keyVal = _computeVisualKey(chnKsx, chnKrx)` считается от пары цепочек, отсортированных по значению, — сама идея верная и симметричная. Но в момент установления сессии пары не равны. У инициатора `chnKrx` выведен из `DH(наш_статик, их_статик)`, а сходящаяся с ним отправляющая цепочка ответчика выводится позже — из `DH(эфемерный_B, эфемерный_A)`, о котором инициатор узнаёт только из первого сообщения ответчика. То есть **до первого входящего сообщения слова у сторон разные**. Пользователь открывает шторку сразу после создания секретного чата, сравнивает — не совпало. Вывод, который он сделает: «меня слушают».

Совпадать слова начинают только в состоянии покоя, когда всё отправленное доставлено и расшифровано обеими сторонами. То есть механизм в принципе рабочий, но момент, в который его показывают, выбран худший из возможных.

**Вторая — слова и хеш считаются от разных ключей.**

```dart
Future<List<({String word, String color})>> getVisualWords(int chatId) async {
  final session = _sessions[chatId];
  return _dr.getVisualWords(session.keyVal);        // keyVal
}

Future<String> computeCheckHash(int chatId) async {
  final keyVal = session.prvKey ?? session.keyVal;  // prvKey
  final hash = await _dr.hashKeyValBytes(keyVal);
  return base64Encode(hash.sublist(0, 4));
}
```

`prvKey` — это **предыдущее** значение (`session.prvKey = session.keyVal` перед обновлением в `decrypt`). Пользователь видит слова от `keyVal`, а «проверка шифрования» сравнивает хеш от `prvKey`. Два разных ответа на один вопрос.

Плюс модульное смещение в самой генерации: `hashBytes[i * 2] % 50` при 256 значениях байта — индексы 0..5 выпадают примерно на 20% чаще остальных, то же с `% 7` для цветов. Для механизма защиты от MITM смещение распределения — плохая мелочь; берите индексы через rejection sampling или расширьте словарь до 64/128 слов.

### СЕКР-1 · Хендшейк летит открытым текстом в обычные, не секретные чаты

`ensureSecretHandshake` проверяет только наличие ключа собеседника:

```dart
final String? partnerPublicKey = await _getPartnerPublicKey();
if (partnerPublicKey == null) return;
```

Проверки `chat.isSecret` здесь **нет** (в `send()` она есть, а здесь нет). А `partnerPublicKey` приходит из `with_user.public_key` в сводке чата и от `is_secret` не зависит. Публичный ключ при этом загружается на сервер для каждого пользователя — `ChatsNotifier._fetch` вызывает `setPublicKey` при каждом обновлении списка чатов.

Значит: открываешь **любой** обычный диалог, и если твой публичный ключ лексикографически больше — приложение отправляет в него сообщение `{"dh":"...","ed":"...","sig":"..."}` обычным текстом через `sendMessage(content: handshakePayload)`.

Что это ломает:

- **Превью в списке чатов.** `_parseHeloMessage` фильтрует HELO только в `ChatMessagesNotifier`. `ChatsNotifier._handleNewMessagePush` его не знает, поэтому в списке чатов последним сообщением показывается сырой JSON.
- **Уведомления.** `NotificationStorage.createAndSave(body: message.content)` — в центре уведомлений появляется `{"dh":"...`.
- **Счётчик непрочитанного.** `newUnreadCount = chat.unreadCount + 1`, потому что `senderId != myUserId`. У собеседника горит непрочитанное на сообщение, которого он в чате не увидит: в списке сообщений оно отфильтровано.
- **Сервер.** Протокольный трафик лежит в базе как обычные текстовые сообщения и остаётся там навсегда.

Хендшейк не должен быть сообщением чата. Нужен отдельный WebSocket-эвент (`e2ee_helo`) вне ленты сообщений. Минимальный костыль на сегодня: `msg_type: 'e2ee_helo'`, скрытый на сервере из истории, из `last_message` и из счётчика непрочитанного.

### БЕЗ-1 · Ключи сессий живут после выхода из аккаунта

```dart
static final Map<int, SecretKey> _sharedSecrets = {};
static final Map<int, DoubleRatchetSession> _sessions = {};
static final Map<int, E2eeSessionStatus> _sessionStatus = {};
static final Map<int, String> _verifiedPeers = {};
```

Четыре `static` карты на классе, который раздаётся обычным `Provider`. Чистятся только в `deleteKeyPair()`, который вызывается из настроек E2EE — но не при выходе из аккаунта.

Вдобавок ключ карт — просто `chatId`, без привязки к пользователю. Вышел из аккаунта A, зашёл в аккаунт B, открыл чат с тем же числовым id — и `_sessions[chatId]` отдаёт сессию предыдущего пользователя. То же на диске: `e2ee.session.<chatId>` в secure storage не привязан к владельцу.

Нужно: очистка всех карт в обработчике logout, и ключи вида `<userId>.<chatId>` и в памяти, и в хранилище.

### БЕЗ-2 · Токен сессии уходит в теле multipart-запроса в дополнение к заголовку

`ChatRepository._httpMultipartUpload`:

```dart
request.headers['Authorization'] = 'Bearer $token';
request.fields['token'] = token;
```

Заголовка достаточно. Дублирование в поле формы означает, что токен попадает в тело запроса — в логи прокси, в отладочные дампы, в любые промежуточные системы, которые пишут body. То же в `downloadMedia`, где токен вообще **только** в теле:

```dart
body: jsonEncode({'token': token, 'file_path': cleanPath}),
```

Вместе с ФЕТЧ-1 и ФЕТЧ-6 из прошлого отчёта это один блок работ: токен передаётся только в `Authorization`, только на свой origin, по allowlist хостов.

### ДИЗ12-1 · Кнопка «Проверить шифрование» ничего не отправляет, но сообщает, что отправила

```dart
Future<void> _runCheckEnc() async {
  setState(() => _checkResult = null);
  final hash = await e2ee.computeCheckHash(widget.chatId);
  setState(() => _checkResult = 'CHK sent. Wait for peer response.\nHash: $hash');
}
```

Никакого сетевого вызова здесь нет. Считается локальный хеш, и в интерфейс выводится «CHK sent. Wait for peer response.» — на английском, в русском приложении, с моношрифтным base64 под ним. Ответа ждать неоткуда: протокольного сообщения CHK не существует, а `verifyCheckHash` не вызывается **ни из одного места в проекте**.

Это пятая находка в линейке фиктивной функциональности после симулированного прогресса загрузки, выдуманной осциллограммы, `'0:30'` и `'MP4'`. И самая неприятная по контексту: она врёт в экране безопасности.

Либо реализовать обмен CHK по-настоящему (отдельный WS-эвент, `verifyCheckHash` на приёме, явный результат «совпало / не совпало»), либо удалить кнопку и оставить сравнение слов и QR.

## КРИП — Double Ratchet и E2EE-сервис (13)

- **КРИП-6** `DoubleRatchetService.completeHandshake` — **мёртвый и опасный код**. `E2eeService.completeHandshake` его не вызывает (и в комментарии честно написано почему: пересборка сессии из эфемерного ключа рассинхронизирует стороны). Метод остался в файле и ждёт, пока кто-нибудь его позовёт. Удалить.
- **КРИП-7** `getOrCreateSession` ничего не создаёт — возвращает `null`, если сессии нет. Параметры `theirPublicKeyBase64` и `isInitiator` **не используются вообще**. Имя и подпись обманывают вызывающего; отсюда и молчаливый откат КРИП-4.
- **КРИП-8** Подпись в HELO ставится только на эфемерный публичный ключ: `_ed.sign(dhsPub.bytes)`. Ни `chatId`, ни времени, ни идентификатора получателя. Такой HELO можно переиграть в другой чат или позже в этот же. Нужно подписывать `chatId || our_static || their_static || dh_pub || timestamp`.
- **КРИП-9** `E2eeService()` в конструкторе делает `unawaited(loadVerifiedPeers())`. Пока чтение из secure storage не завершилось, `_verifiedPeers` пуста, поэтому проверка MITM в `handleHeloMessage` просто пропускается. Окно совпадает со старом приложения — то есть ровно с тем моментом, когда идут хендшейки.
- **КРИП-10** `verifyPeer` пишет `session.peerStaticEd` без проверки на пустоту, а `fromJson` подставляет `peerStaticEd: json['peerStaticEd'] as String? ?? ''`. Подтвердив сессию с пустой идентичностью, получаешь `isPeerVerified == true` навсегда и гарантированный ложный MITM при следующем HELO.
- **КРИП-11** Из состояния `compromised` **нет выхода**. Ни «сбросить сессию», ни «переподтвердить» в UI не существует, а `_sessionStatus` не сбрасывается ничем, кроме полного удаления ключевой пары. Легитимная переустановка приложения у собеседника = навсегда сломанный чат.
- **КРИП-12** Корневой ключ инициализируется сам из себя: `var ratKey = dhOut; var r = await kdfrk(ratKey, dhOut);` — DH-выход используется одновременно как соль и как входной материал, без метки домена. Работает, но это не то, что описано в спецификации Double Ratchet; правильнее `root = HKDF(dh_out, salt: 0, info: "NiosMess-DR-root-v2")`.
- **КРИП-13** `skipKs` ограничен `if (session.numRcv + 100 < until) throw StateError('Too many skipped messages')`, исключение проглатывается в `catch` внутри `decrypt` и превращается в `null`. Пользователь видит пустое сообщение без объяснения.
- **КРИП-14** **У недешифруемого сообщения нет состояния в UI.** `_decryptE2eeMessages` в `catch` кладёт сообщение с пустым `content`, и `message_bubble` рисует пустой пузырь. Нужен явный вид: замок, текст «не удалось расшифровать», действие «запросить повторно».
- **КРИП-15** Вся расшифровка идёт последовательным `for` с `await` на главном изоляте — при 80 сообщениях это 80 последовательных криптооперации до первого кадра. При этом `EncryptedMessageCache` **уже** умеет `Isolate.run`, то есть инфраструктура есть и используется в другом месте того же пути.
- **КРИП-16** `deriveCallKey` выводит ключ звонка из **статического** ECDH: `hkdf.deriveKey(secretKey: shared, nonce: info, info: info)`. Соль равна info, и для одной пары пользователей ключ отличается только `callId`. Компрометация статического ключа раскрывает все прошлые звонки. Ключи звонков надо привязывать к эфемерным ключам сессии.
- **КРИП-17** `Ed25519IdentityService.formatFingerprint` начинается с `base64Decode(base64Encode(publicKeyBytes))` — кодирование и немедленное декодирование одних и тех же байтов. Чистая холостая работа.
- **КРИП-18** `_clearAllSessions` перебирает `_storage.readAll()` и удаляет ключи по префиксу — на каждом выходе это полное чтение всего secure storage. Ключи сессий стоит держать в индексе.

## СЕКР — секретные чаты как функция (11)

- **СЕКР-2** Эхо своего сообщения в секретном чате **сносит все висящие загрузки медиа**. В `_handleNewIncomingMessage`:
    
    ```dart
    if (finalMessage.senderId == myUserId) {
      next.removeWhere((m) => m.id < 0 && m.content == finalMessage.content);
    }
    ```
    
    У пришедшего эха `content` пустой (КРИП-1), а у оптимистичного медиа-сообщения он тоже пустой — `content: (isE2ee && uploadId != null) ? '' : trimmed`. Совпало → удалены все незавершённые отправки файлов. Сопоставлять надо по `localId`.
    
- **СЕКР-3** Хендшейк инициируется **один раз за жизнь провайдера**, из `build()`. Если в этот момент собеседник ещё не загрузил свой публичный ключ, сессия не создастся, а повторной попытки не будет до полного пересоздания провайдера.
- **СЕКР-4** Выбор инициатора — `ourPub.compareTo(partnerPublicKey) <= 0`, сравнение base64-строк статических ключей. Детерминированно и симметрично, это верно. Но если у обеих сторон ключи поменялись (ротация), обе могут одновременно оказаться инициаторами относительно устаревших данных партнёра.
- **СЕКР-5** `_parseHeloMessage` ловит любое текстовое сообщение, начинающееся с `{"dh"`. Пользователь, отправивший такой JSON руками, увидит, что сообщение молча исчезло. В обычном чате — тоже (см. СЕКР-1).
- **СЕКР-6** `ChatsNotifier` ничего не знает про E2EE: превью последнего сообщения для секретного чата всегда пустое, поэтому в списке чатов и в уведомлениях показывается `'...'` (`body = message.content.isNotEmpty ? ... : '...'`). Секретный чат в списке выглядит как сломанный.
- **СЕКР-7** `EncryptedMessageCache.saveMessages` обрезает историю до последних 100 сообщений. Пролистал вверх пять страниц, закрыл чат — осталось 100. Для секретного чата, где это единственная копия открытого текста, обрезание кэша = потеря переписки.
- **СЕКР-8** Все ошибки кэша глушатся в `debugPrint`, включая `Hive.box` без проверки `isOpen`. Если `ensureInitialized` упал, каждая запись и чтение бросают исключение, которое проглатывается — кэш молча не работает вообще, и никто об этом не узнает.
- **СЕКР-9** `sendMessage` при некорректном ответе сервера **фабрикует сообщение**: `id: DateTime.now().millisecondsSinceEpoch`, `senderUsername: 'me'`, `senderDisplayName: 'Me'`. Пользователь видит успешно отправленное сообщение, которого на сервере нет, с id, который никогда не совпадёт с настоящим. То же в `sendComment`.
- **СЕКР-10** Порядок сообщений считается двумя разными способами: `getHistory` сортирует по `id`, `_compareMessages` — по времени, затем по `id`. При расхождении часов клиента и сервера порядок в истории и порядок после вставки нового сообщения различаются.
- **СЕКР-11** Нет ни таймера самоуничтожения на сообщение, ни индикации «прочитано и удалено», ни запрета пересылки из секретного чата. При этом контекстное меню в секретном чате показывает «Переслать»: `isSecret` в `MessageContextMenuSheet` передаётся, но на набор действий не влияет.
- **СЕКР-12** `banUser` и `muteUser` в репозитории бросают захардкоженные русские строки `'Нельзя заблокировать пользователя Support'` — пользовательский текст в слое данных, вне локализации.

## БЕЗ — безопасность и утечки (9)

- **БЕЗ-3** Идентичность собеседника берётся из самого HELO: `theirEdPublicKeyBase64: helo.edPubB64`. Подпись проверяется тем же ключом, который в этом сообщении и лежит, — самоподписанное утверждение. Защищает только TOFU-карта `_verifiedPeers`, и только если пользователь один раз нажал «Подтвердить». Ed25519 собеседника должен приходить с сервера вместе с `partner_public_key`.
- **БЕЗ-4** Ключ кэша сообщений (`niosmess_msg_cache_key_v1`) один на все аккаунты и не привязан к пользователю. Вместе с БЕЗ-1 это означает, что кэш сообщений предыдущего аккаунта остаётся читаемым.
- **БЕЗ-5** Ротация ключа в настройках делает `deleteKeyPair()`, который стирает **все** сессии и **всю** карту подтверждённых собеседников — локально и без уведомления второй стороны. У собеседника сессия остаётся старой, и его сообщения перестают расшифровываться у тебя, а твои — у него. Перерасогласование не запускается: `ensureSecretHandshake` живёт только в `build()` провайдера чата.
- **БЕЗ-6** `_eraseSecretChats` вызывает `getPublicKeyBase64()`, а этот метод **создаёт новую ключевую пару, если её нет**. То есть на сервер для удаления может уйти только что сгенерированный ключ, а не тот, которым шифровались чаты. После этого `setState(() => _hasKey = false)` — и это неправда: пара существует, при следующем входе на экран `_checkKey` её найдёт.
- **БЕЗ-7** Материал сессий (`ratKey`, `dhsSeed`, цепочки) сериализуется в JSON и пишется в secure storage целиком, без версии формата. Миграция схемы невозможна: `fromJson` на старом формате бросит исключение, которое проглотится в `catch`, и сессия молча исчезнет.
- **БЕЗ-8** Нет ограничения на возраст сессии и нет перезаключения. Одна DR-сессия живёт до ротации ключей или переустановки. Плюс не хранится порог по `numSnt`, после которого стоит принудительно сделать DH-шаг.
- **БЕЗ-9** `E2eeSessionStatus.connecting` не имеет таймаута. Собеседник не ответил — статус висит «подключаемся» бесконечно, и в шторке навсегда остаётся спиннер с текстом «Waiting for peer handshake response...».
- **БЕЗ-10** `computeSharedSecret` выводит ключ AES-GCM **прямо из сырого X25519-секрета**, без HKDF и без метки. Для легаси-пути это ещё и означает один и тот же ключ для всех сообщений переписки.
- **БЕЗ-11** `EncryptedMessageCache` хранит у E2EE-сообщения одновременно и `content` (открытый текст), и `e2ee_content` (шифротекст). Кэш зашифрован, так что это не дыра, но дублирование удваивает объём и держит шифротекст там, где он больше не нужен.

## ДИЗ12 — экран 12 слов: разбор (17)

Это `E2eeVerificationSheet` — шторка с 12 словами, отпечатками и кнопками. По M3 Expressive здесь не сделано почти ничего.

- **ДИЗ12-2 · Половина экрана на английском.** Захардкожены без локализации: `'No E2EE session established yet.'`, `'Tap "Initialize" to start the secure handshake with your peer.'`, `'Initialize E2EE'`, `'Waiting for peer handshake response...'`, `'CHK sent. Wait for peer response.'`, `'E2EE v1'`. Остальные строки идут через `context.l10n`. В русском интерфейсе экран безопасности говорит на двух языках.
- **ДИЗ12-3 · Бейдж версии врёт.** `'E2EE v1'` захардкожен, тогда как код согласовывает v2 (`payload = {'v': 2, ...}`). Пользователю показывают версию протокола, которая не используется.
- **ДИЗ12-4 · Семь сырых цветов из палитры Flutter.** `_colorFromName` возвращает `Colors.red`, `Colors.green`, `Colors.amber`, `Colors.blue`, `Colors.pink`, `Colors.cyan`, `Colors.grey.shade100`. Плюс `Colors.green` ещё четыре раза для состояния «подтверждено». Прямое нарушение конвенции репозитория (никаких `Colors.*`), нет адаптации к тёмной теме, а «белое» слово (`grey.shade100`) на светлой поверхности практически не видно.
- **ДИЗ12-5 · Никакой типографики.** Слова — `titleSmall` с `fontWeight: w800` и `letterSpacing: 0.5`, номера — `labelSmall` в том же цвете с альфой 0.7. Главный смысловой элемент экрана визуально мельче заголовка секции. Для сверки голосом нужен крупный, спокойный, читаемый набор.
- **ДИЗ12-6 · Ноль движения.** Ни `AnimatedSwitcher` между четырьмя состояниями, ни `M3SpringCurves`, ни появления слов, ни отклика на подтверждение. Статичный `Wrap` из 12 контейнеров. `flutter_animate` в проекте есть и используется в других местах.
- **ДИЗ12-7 · Нет тактильного отклика.** `HapticService` в проекте есть (соседняя шторка автоудаления им пользуется), здесь не вызывается ни разу — включая подтверждение собеседника, то есть самое значимое действие экрана.
- **ДИЗ12-8 · Семь разных радиусов вручную:** `circular(2)`, `(6)`, `(8)`, `(10)`, `(12)`, `(16)`, `(999)`. `AppRadii` в проекте существует и не используется.
- **ДИЗ12-9 · Альфа вместо тональных ролей.** Фон слова — цвет с `alpha: 0.15`, рамка — тот же цвет с `alpha: 0.35`. В M3 для этого есть контейнерные роли; альфа поверх произвольной поверхности даёт непредсказуемый контраст, особенно в тёмной теме.
- **ДИЗ12-10 · Третий вид «ручки» шторки.** Здесь `32×4` с `onSurfaceVariant` при альфе 0.3, в шторке автоудаления `40×4` с `outlineVariant` при 0.5. Общего компонента нет.
- **ДИЗ12-11 · Состояние не обновляется.** `_sessionInfo` считается один раз в `initState`. Хендшейк завершился, пока шторка открыта — она об этом не узнает и навсегда останется в «Waiting for peer handshake response...».
- **ДИЗ12-12 · Нет обработки ошибки.** `FutureBuilder` проверяет только `!snapshot.hasData`; исключение в `getSessionInfo` даёт бесконечный индикатор загрузки.
- **ДИЗ12-13 · Нет способа сверить слова вне канала.** Ни QR, ни копирования, ни режима чтения вслух. При этом `qr_flutter` в зависимостях, а `my_qr_code_sheet.dart` — готовый пример использования.
- **ДИЗ12-14 · Моношрифт, которого нет.** Отпечатки рисуются `fontFamily: 'monospace'` — такого семейства в проекте не объявлено (есть BricolageGrotesque, Onest, GolosText, PlusJakartaSans, Inter), поэтому берётся системный дефолт и типографика выпадает из остального приложения.
- **ДИЗ12-15 · Жёсткие размеры.** `fontSize: 11` в трёх местах, `letterSpacing: 1.5`, `SizedBox(height: 100)` под индикатор. При увеличенном системном шрифте отпечаток не переносится, а уезжает.
- **ДИЗ12-16 · `_colorFromName` вызывается по четыре раза на слово** прямо в `build` — 48 вызовов на перерисовку, и весь `Wrap` перестраивается на любой `setState`.
- **ДИЗ12-17 · Иерархия кнопок неверная.** Два равных `OutlinedButton.icon` рядом: «Подтвердить» (главное действие экрана) и «Проверить шифрование» (не работает вовсе). Главное действие должно быть `FilledButton`.
- **ДИЗ12-18 · Нет обратного действия.** После подтверждения кнопка становится `onPressed: null` навсегда. Снять подтверждение, посмотреть историю верификации или переподтвердить после смены ключа собеседника невозможно.

### Что сделать с экраном 12 слов — спек в M3 Expressive

1. **Четыре состояния — один переключатель.** `none` / `connecting` / `secured` / `compromised` внутри `AnimatedSwitcher` с `M3SpringCurves.spatial`, 300 мс. Сейчас все состояния свалены в один `Column` набором `if`-ов, из-за чего вёрстка скачет.
2. **Эмблема вместо иконки.** `Icons.security_rounded` заменить на морфящуюся фигуру из `flutter_m3shapes`: «щит в процессе» → «печать подтверждено», с переходом цвета от `tertiary` к `primary` и морфом формы на пружине. Это главный визуальный якорь экрана.
3. **Слова — сетка 3×4, а не `Wrap`.** Фиксированная решётка читается и сверяется голосом гораздо лучше, чем чипы разной ширины. Каждая ячейка — тональная карточка `surfaceContainerHigh` с радиусом из `AppRadii`.
4. **Цвета — из схемы, а не из `Colors`.** Семь слотов маппятся на роли активной схемы (`primary`, `secondary`, `tertiary`, `error` и их контейнерные варианты), при нехватке — через сдвиг тона в HCT, как это уже делает `avatarColorFor`. Слово красится `on*`-ролью на соответствующем контейнере, контраст гарантирован в обеих темах.
5. **Появление с задержкой.** Карточки проявляются каскадом по 40 мс: `opacity` 0→1 плюс `scale` 0.92→1 на пружине. Двенадцать слов «выкладываются» — момент верификации ощущается как событие, а не как список.
6. **Типографика под чтение вслух.** Слово — `titleLarge` с `w700`, номер — надстрочный `labelMedium` в `onSurfaceVariant` с `FontFeature.tabularFigures()`. Отдельный режим «Читать вслух»: полноэкранная раскладка в две колонки крупным кеглем, чтобы держать телефон у лица во время звонка.
7. **Сверка по QR.** Кнопка «Сравнить по QR»: на одной стороне `QrImageView` с байтами защитного кода, на другой — сканер; при совпадении сразу `verifyPeer` плюс `HapticService.confirm()` и морф эмблемы в «подтверждено». Это закрывает и ДИЗ12-13, и бесполезную кнопку CHK.
8. **Кнопки по иерархии M3E.** `FilledButton` «Подтвердить собеседника» на всю ширину, ниже — тональный ряд «Сравнить по QR» / «Скопировать» / «Читать вслух». Мёртвую «Проверить шифрование» убрать до реализации протокола.
9. **Состояние `compromised` — не плашка, а экран.** Полная смена содержимого: контейнер `errorContainer`, объяснение, что именно изменилось (старый и новый отпечаток рядом), и **работающее** действие «Сбросить сессию и переподтвердить». Сейчас выхода из этого состояния нет вообще.
10. **Честная подпись версии.** Бейдж берёт версию из сессии, а не из литерала, и при работе по легаси-пути показывает предупреждение об ослабленном шифровании (КРИП-4).
11. **Живое состояние.** Вместо одноразового `Future` в `initState` — провайдер сессии, на который шторка подписана; хендшейк завершился — экран сам переехал в `secured`. Плюс таймаут на `connecting` с текстом «собеседник не в сети» и кнопкой повтора.
12. **Локализация.** Новые ключи: `e2eeSafetyWordsTitle`, `e2eeSafetyWordsDesc`, `e2eeReadAloud`, `e2eeCompareQr`, `e2eeCopyWords`, `e2eeSessionNoneTitle`, `e2eeSessionNoneDesc`, `e2eeInitAction`, `e2eeWaitingPeer`, `e2eeWaitingPeerTimeout`, `e2eeResetSession`, `e2eeProtocolVersion(version)`, `e2eeWeakEncryptionWarning`.

## НАСТР — экран настроек E2EE (8)

- **НАСТР-1 · Дублирующее действие.** Первая плитка при наличии ключа ведёт на `_rotateKey` («нажмите, чтобы перегенерировать»), и **сразу под ней** вторая плитка «Сменить ключ», вызывающая тот же `_rotateKey`. Ровно тот класс дубликатов, из-за которого мы переделывали настройки.
- **НАСТР-2** `setState(() { _loading = true; }); if (!mounted) return;` — проверка `mounted` стоит **после** `setState` и **до** `await`, то есть не проверяет ничего. Повторено трижды: в `_generateKey`, `_rotateKey` и `_eraseSecretChats`.
- **НАСТР-3** Свой отпечаток на экране не показан, хотя `getSessionInfo` умеет его отдавать (`ourFingerprint`). Это первое, что пользователь ищет в настройках шифрования.
- **НАСТР-4** Нет списка подтверждённых собеседников и нет статусов сессий по чатам, хотя `_verifiedPeers` и `_sessionStatus` это знают. Управлять доверием из настроек нельзя.
- **НАСТР-5** Ошибки выводятся сырым `Text(_error!, style: TextStyle(color: scheme.error, fontSize: 13))` вместо `AppErrorBanner` или `AppToast`, которые в проекте есть.
- **НАСТР-6** `_loading` блокирует плитки через `enabled: !_loading`, но визуального индикатора процесса нет — при генерации ключа экран просто перестаёт реагировать.
- **НАСТР-7** Все три действия необратимы и разрушительны, но различаются только цветом иконки (`tertiary`, `secondary`, `error`). «Стереть секретные чаты» должно быть отделено в собственную секцию с явным предупреждением.
- **НАСТР-8** После ротации ключа ничего не перерасогласовывается (БЕЗ-5), и пользователю об этом не сообщают — ни экран, ни тост не говорят, что существующие секретные чаты придётся переустанавливать с двух сторон.

## АВТОУД — шторка автоудаления (7)

- **АВТОУД-1** Одиннадцать захардкоженных русских строк: `'Автоудаление сообщений'`, `'Новые сообщения будут автоматически удаляться через выбранный период'`, `'Отключено'`, `'24 часа (1 день)'`, `'7 дней (1 неделя)'`, `'1 месяц (30 дней)'`, `'Свой срок: N дн.'`, `'1 день'`, `'365 дней'`, `'Сохранить'`, тост `'Автоудаление сообщений обновлено'`.
- **АВТОУД-2** Минимальный интервал — сутки. При этом модель умеет минуты: `formattedAutoDeleteDuration` обрабатывает `sec < 3600` и возвращает `'$m мин.'`. То есть бэкенд поддерживает короткие сроки, а UI их выставить не даёт — для секретного чата это как раз самые нужные значения.
- **АВТОУД-3** Радиогруппа собрана вручную из `Container` с рамкой и `Icons.radio_button_unchecked_rounded`. Нет семантики радиогруппы для скринридера, нет группового фокуса. В M3 для этого есть `RadioGroup` и `SegmentedButton`.
- **АВТОУД-4** `ListTile` внутри `Container` с `BorderRadius.circular(16)` и `Material(type: MaterialType.transparency)` — рябь не обрезается по радиусу и вылезает за скруглённые углы. Тот же класс, что КМЕНЮ-2.
- **АВТОУД-5** `Slider` от 1 до 365 с `divisions: 364` — попасть в нужное значение пальцем невозможно. Нужны шаг-пресеты или ввод числа.
- **АВТОУД-6** `ref.invalidate(chatsProvider)` на сохранение → полный повторный запрос списка чатов, а это два последовательных сетевых запроса (ПЛАВ-10). Достаточно локального `upsertChat`.
- **АВТОУД-7** Таймер автоудаления никак не показан в самом чате: ни в шапке, ни на сообщениях. Пользователь включил и забыл, а сообщения исчезают без объяснения.

## Цвета, фейки, локализация

- **ЦВЕТ-21** Семь `Colors.*` в `_colorFromName` плюс четыре `Colors.green` в `e2ee_verification_sheet` — прямое нарушение конвенции репозитория в экране безопасности.
- **ЦВЕТ-22** Цветовые слоты слов не связаны со схемой темы: «белое» слово в светлой теме невидимо, «жёлтое» на светлом фоне не читается.
- **ЦВЕТ-23** Тонирование альфой (`0.15` фон, `0.35` рамка, `0.7` номер) вместо тональных контейнерных ролей — по всему файлу.
- **ФЕЙК-7** «Проверить шифрование» сообщает «CHK sent», ничего не отправив (ДИЗ12-1).
- **ФЕЙК-8** Бейдж `'E2EE v1'` при фактическом протоколе v2 (ДИЗ12-3).
- **ФЕЙК-9** «Отпечаток собеседника» равен твоему собственному, пока хендшейк не завершён (КРИП-3).
- **ФЕЙК-10** `sendMessage` фабрикует успешно отправленное сообщение при некорректном ответе сервера (СЕКР-9).
- **L10N-8** Около 30 новых захардкоженных строк: 6 английских в шторке верификации, 11 русских в автоудалении, 2 русских исключения в `chat_repository`, плюс ранее найденные в провайдере.

## Порядок работ

<aside>
1️⃣

**Чтобы оно вообще работало.** КРИП-1 полностью (локальное хранение своего плейнтекста, пропуск своих сообщений в расшифровке, признак «расшифровано» и возможность обнулить `e2eeContent` в `copyWith`). КРИП-2 (`skipKs` в сериализацию, удаление ключа только после успеха). СЕКР-2 (дедуп по `localId`). Без этого секретные чаты не работают, а не «работают с дефектами».

</aside>

<aside>
2️⃣

**Безопасность.** КРИП-3 (не подставлять свой Ed25519 как ключ собеседника), БЕЗ-3 (получать Ed25519 с сервера), КРИП-4 (убрать молчаливый откат на v1), БЕЗ-1 плюс БЕЗ-4 (очистка при logout, ключи с привязкой к пользователю), БЕЗ-2 (токен только в заголовке, allowlist хостов — одним блоком с ФЕТЧ-1).

</aside>

<aside>
3️⃣

**Протокол.** СЕКР-1 (хендшейк отдельным WS-эвентом, вне ленты сообщений, вне превью и вне непрочитанного), КРИП-8 (подпись с привязкой к чату и времени), КРИП-6 (удалить мёртвый `completeHandshake`), КРИП-11 (выход из состояния `compromised`), КРИП-9 (дождаться загрузки `_verifiedPeers` до первой проверки).

</aside>

<aside>
4️⃣

**Верификация, чтобы ей можно было пользоваться.** КРИП-5 (одинаковые слова у сторон: считать защитный код от стабильного корневого материала сессии, а не от текущих цепочек; слова и хеш — от одного и того же ключа), ДИЗ12-1 (убрать или реализовать CHK), КРИП-14 (явный вид недешифруемого сообщения).

</aside>

<aside>
5️⃣

**Дизайн 12 слов.** Двенадцать пунктов спека выше. Начинать с пунктов 1, 3, 4 и 6 — состояния, сетка, цвета из схемы и типографика под чтение вслух: они дают почти весь эффект.

</aside>

<aside>
6️⃣

**Остальное.** НАСТР-1 (убрать дубль), НАСТР-3 (показать свой отпечаток), НАСТР-4 (список подтверждённых), АВТОУД-1/2/3 (локализация, короткие интервалы, настоящая радиогруппа), СЕКР-7 (не обрезать кэш секретного чата до 100), L10N-8.

</aside>

## Критерии приёмки

- Отправил 20 сообщений в секретном чате, сделал pull-to-refresh, свернул и развернул приложение, пролистал историю вверх на 5 страниц — **ни одно сообщение не стало пустым**.
- Перезапустил приложение — вся переписка секретного чата читается, включая сообщения, пришедшие не по порядку до перезапуска.
- Открыл обычный диалог — в списке чатов и в уведомлениях **нет** JSON с `dh`, счётчик непрочитанного не растёт на протокольные сообщения.
- Два устройства, свежий секретный чат: 12 слов совпадают **сразу после установления сессии**, до обмена сообщениями.
- Отпечаток собеседника отличается от своего; после «Подтвердить» повторный хендшейк не выдаёт ложный MITM.
- Сессии нет — отправка либо ждёт хендшейка, либо явно помечена как ослабленная. Молча по v1 ничего не уходит.
- Сообщение, которое не удалось расшифровать, показано явно, с действием повтора, а не пустым пузырём.
- Вышел из аккаунта, зашёл в другой — ни одной сессии, ни одного подтверждённого собеседника, ни одного сообщения из кэша предыдущего аккаунта.
- `rg -n "Colors\\." lib/widgets/chat/e2ee_verification_sheet.dart` пусто; экран 12 слов корректно выглядит в светлой и тёмной теме и при увеличенном системном шрифте.
