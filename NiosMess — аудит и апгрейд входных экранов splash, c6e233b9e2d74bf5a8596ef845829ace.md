## Главный вывод

Входная воронка выглядит как продукт, который несколько раз менял модель авторизации и ни разу не убирал за собой. Сейчас в `lib/screens` лежит **41 КБ кода четырёх экранов, недостижимых ни при каких условиях**, второй онбординг с выбором языка и часового пояса, который невозможно увидеть, и логин, где на мобильном работает худший из двух реализованных OAuth-путей, а лучший уже написан и не вызывается.

При этом всё, что пользователь реально видит, — это три экрана: splash, онбординг, логин. На них: ни одной `M3SpringCurves`, три разных представления одного логотипа за пять секунд, четырнадцать разных значений длительности анимаций, `boxShadow` на главной эмблеме продукта и запрос системных разрешений раньше, чем человек увидел хотя бы один экран.

## 1. Мёртвый код: 41 КБ недостижимых экранов

В роутере четыре маршрута объявлены как заглушки-редиректы:

| Файл | Размер | Маршрут | Что делает роутер |
| --- | --- | --- | --- |
| `verify_email_screen.dart` | 10 КБ | `/verify-email` | `redirect: (context, state) => '/login'` |
| `two_fa_screen.dart` | 12,4 КБ | `/2fa` | `redirect: (context, state) => '/login'` |
| `reset_password_request_screen.dart` | 7 КБ | `/reset-password/request` | `redirect: (context, state) => '/login'` |
| `reset_password_confirm_screen.dart` | 11,6 КБ | `/reset-password/confirm` | `redirect: (context, state) => '/login'` |
| `register_screen.dart` | 377 Б | `/register` | строит `LoginScreen(...)` напрямую, файл не импортирован |

Ни один из этих пяти файлов **не импортирован в `app_router.dart`**. Они существуют только потому, что Dart не удаляет неиспользуемые файлы из дерева проекта: `flutter analyze` их проверяет, а приложение открыть не может.

Внутри мёртвой зоны есть навигация друг на друга, которая тоже никуда не ведёт:

- `reset_password_request` при успехе делает `context.go('/reset-password/confirm?email=...')` → редирект на `/login`;
- `verify_email` при успехе делает `context.go('/setup')` → см. раздел 2.

### Мёртвая половина `auth_provider.dart`

Недостижимы, потому что их вызывают только мёртвые экраны:

- `login({identifier, password})` — вызывается ровно из одного места: `verifyEmail()`;
- `register(...)` — не вызывается нигде, UI регистрации в приложении отсутствует;
- `verifyEmail(...)`, `requestPasswordReset(...)`, `confirmPasswordReset(...)`, `verifyTwoFa(...)`, `setPendingIdentifier(...)`;
- поля `_pendingEmail` и `_pendingPassword`;
- флаг `AuthActionResult.requiresTwoFa` — его никто не читает.

Два отдельных замечания по этому коду:

<aside>
⚠️

`_pendingPassword` хранит пароль пользователя **в открытом виде в поле нотифаера**, живущего всё время работы приложения, и нужен только в мёртвой ветке автологина после подтверждения email.

</aside>

И логическая дыра на будущее: `login()` умеет вернуть `requiresTwoFa: true`, но обработчика для этого нет ни одного, а экран 2FA недостижим. Если бы вход по паролю работал, аккаунт с включённым 2FA просто не смог бы войти.

## 2. Два онбординга, и показывается не тот

В проекте два независимых онбординга:

- `OnboardingScreen` (`/onboarding`, 12 КБ) — три слайда с Lottie: звонки, чаты, скорость;
- `SetupOnboardingScreen` (`/setup`, 27 КБ) — три страницы: приветствие, **выбор языка**, **выбор часового пояса** с поиском по зонам и живыми часами.

Оба вызывают `sessionProvider.completeOnboarding()`. Оба реализуют свой `PageView`, свои точки-индикаторы (24/10 px, радиус 5, 300 мс `easeInOut` против 26/10 px, радиус 999, 320 мс без кривой) и свои анимации входа страницы.

Второй из них **невозможно увидеть**:

```dart
// app_router.dart, redirect
if (isAuth && (path == '/login' || ... || path.startsWith('/setup') || ...)) return '/main/chats';
```

- Авторизованного пользователя гард уводит с `/setup` на `/main/chats`.
- Неавторизованный на `/setup` попасть может (`/setup` входит в `isPublic`), но `_finish()` делает `context.go('/main/chats')`, и гард `!isAuth && !isPublic` тут же отправляет его на `/login` — **при уже записанном `completeOnboarding()`**. То есть шаг выбора языка и таймзоны теряется навсегда: повторно онбординг не покажется.
- Единственное место, которое вело на `/setup`, — мёртвый `verify_email_screen`.

Итог: самая полезная часть первого запуска — язык и часовой пояс — существует, оплачена 27 КБ кода и недоступна. Telegram ровно это и спрашивает первым делом.

## 3. Splash: две копии политики роутинга и разрешения до продукта

`_startFlow()` содержит собственную копию логики маршрутизации, которая уже есть в `redirect` роутера. Это даёт воспроизводимый артефакт:

<aside>
🐛

`onboardingCompleted` живёт в `SharedPreferences`, а сессия — в `FlutterSecureStorage`. Если prefs очищены или не восстановились, а secure storage восстановился из бэкапа, splash отправляет авторизованного пользователя на `/onboarding`, откуда гард роутера немедленно возвращает его на `/main/chats`. Пользователь видит вспышку онбординга при каждом запуске.

</aside>

Остальное по сплэшу:

- `PermissionService().requestInitialPermissionsIfNeeded()` вызывается **в первом же постфреймовом колбэке, до логина**. Системные диалоги разрешений прилетают человеку, который ещё не видел ни одного экрана продукта и не понимает, за что даёт доступ. Эталонные мессенджеры запрашивают разрешение в момент, когда оно нужно: микрофон — при первом звонке, уведомления — после входа.
- `_rotationController` — `AnimationController(duration: 24 s)..repeat()` на экране, который живёт 350 мс. Один оборот не успевает пройти и на 2 %.
- На тот же логотип одновременно навешен второй аниматор: `.animate(onPlay: repeat(reverse: true)).scale(1100 ms)`. Два независимых источника анимации на одном виджете.
- Фон — `AnimatedMeshBackground`, тот самый P0 из плана плавности (15-секундный `repeat`, `MediaQuery.sizeOf` на кадр). Все остальные auth-экраны уже используют `M3OrganicBackground` с tier-детектом и `RepaintBoundary`. Splash остался на старом.
- Скрытый `BackdropFilter` 10×10 под `Opacity(0.01)` для прогрева шейдера блюра. Идея правильная, место неправильное: это должно быть в разогреве в `main.dart`, а не в дереве экрана; плюс `Opacity(0.01)` создаёт отдельный composited-слой, а на Tier C блюр вообще не используется, и прогрев может оказаться бесполезным.
- `splashGraphicsOptimization` показывается **только на не-Android и не-iOS**, то есть текст про оптимизацию графики видит только веб- и десктоп-пользователь, у которого сплэш и так пролетает за 350 мс.
- Нет обработки ошибок. Если `ensureLoaded()` бросит исключение (повреждённый secure storage, сбой чтения prefs), `_startFlow()` упадёт в необработанный `Future`, и пользователь **навсегда останется на сплэше** без сообщения и без кнопки «Повторить».

## 4. Логин через Nios ID: на мобильном живёт худший из двух путей

В `login_screen.dart` реализованы **два** OAuth-пути:

1. **Authorization Code + PKCE** — `_checkOAuthReturn()` → `_handleOAuthCallback()` → `EphemeralStorage` с `verifier`/`state` → `exchangeAuthCode()`. Срабатывает только если в `Uri.base` есть `?code=`, то есть **исключительно в веб-сборке**.
2. **Device Flow (RFC 8628)** — `_startNiosIdAuth()` → `requestDeviceCode()` → открыть браузер → поллинг токена. Это то, что выполняется по кнопке «Войти через Nios ID` на всех платформах.

Device flow придуман для телевизоров, консолей и CLI — устройств без браузера и клавиатуры. На телефоне он означает: уйти в браузер, руками переписать шестисимвольный код, подтвердить, вернуться в приложение и ждать поллинг. На мобильном правильный путь — PKCE с возвратом по deep link или через системный auth-таб. Он написан и не используется.

Что ещё не закрыто в device-карточке:

- **Нет таймера жизни кода.** `deviceResp.expiresIn` известен, пользователю не показывается. Нет состояния «код истёк» и кнопки «получить новый».
- **Нет QR-кода.** `verificationUriComplete` уже есть — из него делается QR, и это мгновенно закрывает кросс-девайс вход, как в Telegram Desktop. Сейчас вместо этого ручной ввод шести символов.
- **Нет состояния «ждём подтверждения в браузере»** — только бесконечный `AppLoadingIndicator` рядом с заголовком, без указания, что вообще происходит и чего ждать.
- **Нет проверки сети.** `connectivityProvider` в проекте есть, логин его не использует. Нажатие «Войти» без сети даёт текст сырого исключения в тосте.
- **Два индикатора загрузки на одном экране:** `PulseLoadingIndicator(size: 48)` в оверлее и `AppLoadingIndicator` в кнопке и карточке. Два компонента для одной роли.
- `PopScope` показывает `loginTapAgainToExit` («нажмите ещё раз для выхода»), а вызывает `SystemUtils.minimizeApp()` — сворачивание, не выход.

### Несогласованная навигация онбординг → логин

```dart
// onboarding_screen.dart, _handleGetStarted
if (authenticated) {
  context.go('/main/chats');
} else {
  context.push('/login');   // ← push, не go
}
```

`push` кладёт логин **поверх** уже пройденного онбординга. Системный «назад» перехватывается в `PopScope(canPop: false)` логина и вместо возврата показывает «нажмите ещё раз» и сворачивает приложение — при живом экране онбординга в стеке под ним. В соседней ветке того же метода используется `go`.

## 5. Четыре копии одного экрана

`verify_email`, `reset_password_request`, `reset_password_confirm` и отчасти `two_fa` повторяют руками один и тот же скелет:

```
M3OrganicBackground(showBackButton: true, showThemeToggle: true, onBack: () => context.go('/login'))
  → SafeArea → Center → ConstrainedBox(maxWidth: …) → SingleChildScrollView(padding …) → Form
    → M3Container(Shapes.c9_sided_cookie, 64×64, primaryContainer) + Icon(32)
    → headlineSmall w900 letterSpacing -0.5
    → bodyMedium onSurfaceVariant
    → поля
    → Material(primary, radius 28) + InkWell + Container(height 54) + Icon + Text
```

- `maxWidth` в воронке: **440** (login), **420**, **420**, **380** — четыре разных значения для одной и той же роли.
- Главная кнопка собрана руками из `Material` + `InkWell` + `Container` в четырёх местах, а на логине для того же — `FilledButton`. Два способа сделать одну кнопку, с разными ripple, разной высотой (54 против 56) и разным поведением disabled.
- Бейдж-иконка `M3Container(Shapes.c9_sided_cookie, 64)` скопирован трижды.
- В роутере `/web`, `/login` и `/register` — три идентичных `pageBuilder` с одним и тем же блоком четырёх query-параметров.

Нужен один `AuthScaffold({icon, title, subtitle, children, primaryAction})` и один `AuthPrimaryButton`.

## 6. Логотип: три разных представления за пять секунд

| Экран | Что рисуется |
| --- | --- |
| Splash | `M3Container.c9SidedCookie(140)`  • `niosmess_logo_tintable.svg(96)`, вращение 24 с |
| Onboarding | `AppLogoMark(size: 80)` |
| Login | `niosmess_n_mark.svg` внутри `Container(88, BorderRadius.circular(26))` с `boxShadow(blur 36)` |

Три ассета, три формы, три размера, ноль преемственности. За первые пять секунд знакомства с продуктом бренд-знак меняется дважды и оба раза резко. Это как раз то, что читается как «дешёвый» интерфейс.

Целевое решение в духе M3 Expressive: один `Hero` через всю воронку плюс морфинг формы `c9_sided_cookie` → squircle, с пружиной из `M3SpringCurves`. Один ассет.

Отдельно: на главной эмблеме продукта стоит `BorderRadius.circular(26)` при подключённом `flutter_m3shapes`, который используется на всех остальных экранах воронки. Самая скучная форма — на самом важном экране.

## 7. OTP-ввод, из которого нельзя выйти

В `verify_email` и `reset_password_confirm` код вводится через `CodePreview` плюс прозрачный `TextFormField` поверх в `Stack`. Последствия:

<aside>
🚫

Валидатор возвращает **пустую строку** как сообщение об ошибке: `if (length != 6) return '';`. Все бордеры поля выставлены в `InputBorder.none`. В результате при неполном коде нажатие на кнопку не делает ничего и не показывает ничего — ни текста, ни подсветки. Полный тупик для пользователя.

</aside>

- `enableInteractiveSelection: false` плюс прозрачный текст: **вставить код из письма невозможно**, только набрать вручную. При этом объявлен `autofillHints: [AutofillHints.oneTimeCode]`, который как раз для автозаполнения.
- Нет кнопки «Отправить код заново» и таймера до повторной отправки — обязательный элемент любого OTP-флоу.
- Email рисуется в read-only контейнере без возможности исправить. Если `initialEmail == null`, получается пустой серый контейнер с иконкой конверта и ничем.
- `onChanged: (_) => setState(() {})` — полная перестройка экрана на каждую цифру.
- Валидация нового пароля — только `length < 6`. Нет подтверждения пароля, нет индикатора надёжности.

## 8. Экран 2FA: шум вместо Expressive

- Шесть точек PIN получили **шесть захардкоженных цветов** `Color(0xFF5B8DEF)`, `0xFF6ED0F6`, `0xFFF67599`, `0xFF9E86F8`, `0xFF5FE1B5`, `0xFFFF8B70` и **шесть разных форм** (`c9_sided_cookie`, `triangle`, `square`, `c4_sided_cookie`, `gem`, `flower`). Это не выразительность, это визуальный шум и прямое нарушение правила «никаких хардкод-цветов, только схема». M3 Expressive-решение: одна форма, морфинг и увеличение при заполнении, акцент из `ColorScheme`.
- Ввод возможен **только через собственную цифровую клавиатуру**. На десктопе и в вебе (где `M3OrganicBackground` специально рисует карточку на 840+ px) физическая клавиатура не работает, вставка из буфера не работает, `Enter` не отправляет. `autofillHints.oneTimeCode` здесь не объявлен вообще, хотя в email-верификации он есть.
- Нет «Использовать код восстановления», нет «Отправить снова», нет «Другой способ» — стандартный набор для 2FA.
- При неверном коде: `_pin = ''` и тост. Нет shake-анимации, нет счётчика попыток, нет индикации блокировки.
- `if (auth.busy)` **полностью заменяет клавиатуру** индикатором → скачок layout на пол-экрана при каждой отправке.
- `AnimatedScale` внутри `AnimatedContainer` на каждой точке, кривая `Curves.easeOutBack`.

## 9. Производительность

- **`_OrganicBlobsPainter.paint()`** создаёт заново пять `Path`, пять `Paint` и `MaskFilter.blur(BlurStyle.normal, 54.0)` на каждую перекраску. Перекраска происходит при смене темы, повороте, ресайзе окна и любом изменении размеров — включая появление клавиатуры. Это ровно тот P0, который вычистили из `pulse_scaffold_body.dart`; здесь он остался. Спасает только `RepaintBoundary` и статичность. Фикс: закешировать результат в `ui.Picture` или `toImageSync` по образцу `WallpaperImageCache`.
- **`WidgetsBinding.instance.runtimeType.toString().contains('Test')`** — тестовый хак в продакшн-коде, и он выполняется внутри `LayoutBuilder.builder`, то есть строковая аллокация на каждый layout-проход, включая каждый кадр анимации клавиатуры.
- **Onboarding:** три `Lottie.asset(repeat: true)` без `errorBuilder` и без `frameRate`. `PageView.builder` строит соседние страницы, поэтому одновременно проигрываются две Lottie. Поля `_SlideData.icon` и `_SlideData.tintColor` объявлены и не читаются — судя по всему, `icon` задумывался как фолбэк при отсутствии ассета, но фолбэка нет.
- **Setup:** `Timer.periodic(1 s)` с `setState` перестраивает все три страницы `PageView`, хотя часы нужны только на третьей.
- **Переходы:** вся воронка использует дефолтный `MaterialPage`. M3E-переход, который в проекте есть, к входным экранам не подключён. Splash → onboarding → login — три стандартных резких перехода.

## 10. Нарушения M3 Expressive и правил репозитория

- **Ни одной `M3SpringCurves` во всей воронке.** Вместо них: `easeOutBack`, `easeInOutCubic`, `easeInOut`, `easeOut`, `easeOutCubic`. Правило репозитория — «always `M3SpringCurves`».
- **Четырнадцать разных длительностей:** 150, 200, 240, 300, 320, 350, 360, 400, 420, 450, 480, 500, 800, 1100 мс. Плюс задержки 100/150/200/350/500 мс. Системы движения нет.
- **`boxShadow`** на hero-эмблеме логина (blur 36, spread −2), на оверлее авторизации (blur 30) и `elevation: 8` на desktop-карточке `M3OrganicBackground` — нарушение правила «без резких `BoxShadow`, использовать тональные `surfaceContainer*`». Смешение elevation-модели M2 с тональной моделью M3.
- **Радиусы вперемешку:** 5, 6, 16, 18, 20, 22, 26, 28, 32, 36, 999. `AppRadii` из `expressive_tokens.dart` не используется нигде в воронке.
- **Альфы руками:** 0.2, 0.25, 0.3, 0.35, 0.4, 0.45, 0.5, 0.55, 0.6, 0.62, 0.65, 0.7, 0.72, 0.8, 0.85, 0.86, 0.92, 0.98 — восемнадцать значений на глаз.
- **Переключатель темы** в `M3OrganicBackground` жёстко ставит `light` или `dark`, поэтому из входной воронки нельзя вернуться к `ThemeMode.system` — та же болезнь, что была найдена в настройках внешнего вида.
- **Нет `Semantics` и tooltip** на переключателе темы, точках PIN (скринридер не сообщит, сколько цифр введено) и на копировании кода.

## 11. Локализация

- Четыре сырые строки на логине: `'Не удалось начать авторизацию: …'`, `'Не получен токен доступа'`, `'Ошибка входа Nios ID: …'`, `'Авторизация...'`. Две из них интерполируют текст исключения прямо в UI.
- `context.l10n.localeName.startsWith('ru')` плюс два хардкодных варианта строки — **ручная локализация внутри кода** в трёх экранах. Анти-паттерн в квадрате: и хардкод, и самодельная логика локали при работающем `gen-l10n`.
- `'NiosMess'` вбит строкой на логине, при том что splash и онбординг используют `context.l10n.appName`.

## 12. Чего критически не хватает

- **QR-вход.** Инфраструктура device flow уже есть, нужен только рендер `verificationUriComplete` в QR.
- **Таймер жизни кода и повторная выдача.**
- **Offline-состояние и retry** на логине и сплэше.
- **Объяснение «Что такое Nios ID».** Пользователь видит незнакомый бренд и одну кнопку. Нужен короткий explainer в одну строку и раскрывающийся блок.
- **Deep-link возврат из браузера** вместо ручного переписывания кода.
- **Версия и канал сборки на логине** — для альфы с самодельным OTA это дешёвый и очень полезный элемент.
- **«Не могу войти» / поддержка.** Маршрут `/chat/direct/support` до логина недоступен по определению, значит нужна ссылка на веб-форму.
- **Биометрический app-lock** при повторном запуске.
- **Фокус, `Enter` и вставка** на десктопе; a11y-метки.

## Целевая структура входа

1. **`/` splash** — только ожидание гидратации, обработка ошибки и кнопка «Повторить». Решение о маршруте принимает исключительно `redirect` роутера; собственная копия политики удаляется.
2. **`/onboarding`** — три слайда плюс четвёртый шаг «Язык и регион», забранный из `/setup`. Завершение: `go('/login')`, не `push`.
3. **`/login`** — единственный экран авторизации. Карточка Nios ID: основная кнопка, QR и код рядом, таймер жизни кода, состояние «ждём подтверждения», explainer, offline-состояние, версия сборки в футере.
4. **`/legal/*`** — без изменений.
5. **Удаляются:** `/setup`, `/register`, `/verify-email`, `/2fa`, `/reset-password/*` и соответствующие файлы экранов, вместе с мёртвыми методами `auth_provider`.

## Риски

- **Удаление 2FA и сброса пароля закрывает fallback.** Перед фазой 1 нужно подтвердить на бэкенде, что клиентский пароль-флоу действительно выведен из эксплуатации и что Nios ID никогда не вернёт `twoFaRequired` в ответе на `loginNiosId`. Если вернёт — вместо удаления нужен корректный экран 2FA, подключённый к роутеру.
- **Device flow может быть единственным поддерживаемым на сервере.** PKCE-путь в приложении написан, но redirect URI под мобильную схему может быть не зарегистрирован в Nios ID. Фаза 5 начинается с проверки этого, а не с кода.
- **Перенос `PermissionService` в контекстные точки** затрагивает чат, звонки и уведомления — это правки за пределами входной воронки, их нужно вести отдельным списком.
- **`AnimatedMeshBackground` может использоваться не только на сплэше.** Перед удалением проверить все потребители: со сплэша убирается использование, сам виджет удаляется только если потребителей не осталось.
- **Слияние онбордингов меняет `session.onboardingCompleted`.** У существующих пользователей флаг уже выставлен, и новый шаг языка они не увидят. Нужно либо версионировать флаг, либо оставить шаг доступным из настроек (он там уже есть — `/settings/language-region`).
