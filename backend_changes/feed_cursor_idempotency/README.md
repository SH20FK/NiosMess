# Feed cursor pagination & creation idempotency (клиент + сервер)

Дата: 2026-11-16. Патч парный: `pulse_flutter` (клиент) + `server_core` (бэкенд).

## Зачем

1. **Дубли постов/комментариев.** У `create_post`/`comment_post` не было ключа
   идемпотентности: таймаут после успешного коммита → клиент решал, что запрос
   не дошёл, повтор отправлял второй пост/комментарий.
2. **Пропуски в ленте.** Пагинация была номерной (`page=1,2,3…`): новые посты
   сдвигали страницы, и часть постов при листании пропускалась.

## Сервер (`server_core`)

### Схема (миграции автоматические, `app/migrations.py`)

- `posts.client_post_id VARCHAR(64)` + уникальный индекс
  `ix_posts_client_post_id (author_id, client_post_id)`.
- `post_comments.client_comment_id VARCHAR(64)` + уникальный индекс
  `ix_post_comments_client_id (author_id, client_comment_id)`.
- Комментарии каналов идут в `messages` и используют существующую колонку
  `client_message_id` с уже действующим уникальным индексом
  `ix_secret_message_client_id (chat_id, sender_id, client_message_id)`.

### `get_feed`

- Принимает `before_id` — watermark (максимальный `id` поста), который клиент
  получает с первой страницы и передаёт со второй и далее.
- Обе ветки выборки фильтруют `Post.id <= before_id`, поэтому набор постов
  стабилен во время листания: новые публикации не сдвигают страницы.
- Ответ дополнен полями `pagination: "cursor"`, `before_id`, `has_more`.
- Старые клиенты (без `before_id`) работают как раньше — фильтр по `max(id)`
  ничего не отсекает, срез по `offset` прежний.

### `create_post`

- Принимает `client_post_id`. Если пост с таким ключом у автора уже есть,
  возвращается он же (проверка **до** обработки upload-сессий — повтор
  приходит с уже потраченными `upload_ids`).
- Гонка двух одинаковых запросов: уникальный индекс отбивает второй,
  `IntegrityError` ловится и превращается в тот же ответ с существующим постом.
- Ответ идемпотентного повтора: `message: "Post already created"`,
  `post_id`, `idempotent: true`, плюс полный отрендеренный пост.

### `comment_post` / `post_comment`

- Принимают `client_comment_id`; повтор возвращает существующий комментарий,
  гонка закрыта уникальным индексом так же, как у постов.

## Клиент (`pulse_flutter`)

- `NiosgramNotifier`: хранит `_feedCursor` (из `before_id` ответа, сбрасывается
  на refresh/build/смене аккаунта) и передаёт его в `loadMore`; `has_more`
  из ответа приоритетнее расчёта по длине страницы (старый сервер поля не
  присылает — работает прежняя эвристика).
- `createPost(...)` принимает `clientPostId`; экран создания поста генерирует
  UUID один раз на попытку публикации, переиспользует при повторе после
  «статус неизвестен» и сбрасывает при изменении текста/медиа или успехе.
- Комментарии: `PostCommentsRepository.send(..., clientCommentId)`; провайдер
  держит карту `(text, reply_to_id) → key`, поэтому повтор после ошибки идёт
  с тем же ключом (in-flight дедупликация уже была).

## Совместимость

- Сервер: без ключей и `before_id` поведение прежнее (все параметры опциональны).
- Клиент: против старого сервера `client_post_id` игнорируется, `before_id`
  возвращается тем же отсутствием `pagination`-полей — клиент остаётся на
  номерной пагинации. Клиентский «verify после неизвестного статуса» в
  `create_post_screen` сохранён как второй рубеж.
