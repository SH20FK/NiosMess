## 🔴 Блокеры

### РОУТ-1. Кнопка «Позвонить» в профиле физически не может открыть экран звонка

В `app_router.dart` маршруты объявлены в таком порядке:

```dart
GoRoute(path: '/call/:callId', ...)   // ← объявлен ПЕРВЫМ
GoRoute(path: '/call/dm/:username', ...)
GoRoute(path: '/call/outgoing', ...)  // ← никогда не сматчится
```

go_router подбирает маршруты **в порядке объявления**, первый полный матч выигрывает. `/call/outgoing` — два сегмента, `/call/:callId` — тоже два. Значит `context.push('/call/outgoing', extra: OutgoingCallArgs(...))` матчится на `/call/:callId` с `callId = 'outgoing'` и строит `ActiveCallScreen`.

`ActiveCallScreen` при `session == null` рендерит `Scaffold` с пустым AppBar и центрированным `AppLoadingIndicator`. Без таймаута, без ошибки, без retry.

То есть **та самая «страница загрузки чего-то»**, на которую ты жаловался, никуда не делась — весь новый `OutgoingCallScreen` (12 821 B) недостижим из профиля. Он достижим только через `/call/dm/:username`.

Что выдаёт, что про это правило в файле знают: `/chat/create` объявлен **до** `/chat/:chatId` — там сделано правильно.

Фикс: поднять `/call/outgoing` и `/call/dm/:username` выше `/call/:callId`. Плюс тест роутера (ТЕСТ-2).

### РОУТ-2. Переключение табов, вероятно, падает в release-сборке

`widgets/nav/tab_shared_axis_switcher.dart`:

```dart
final RenderObject? object = _boundaryKey.currentContext?.findRenderObject();
// debugNeedsPaint читается ВНЕ try/catch
if (object is! RenderRepaintBoundary || object.debugNeedsPaint) return;
_disposeSnapshot();
try { _snapshot = object.toImageSync(...); } catch (_) { ... }
```

`RenderObject.debugNeedsPaint` во Flutter реализован через `late bool result;`, который присваивается только внутри `assert(...)`. В документации самого Flutter прямо написано «In release builds, this throws» — в release/profile assert вырезан, переменная остаётся неинициализированной, геттер кидает `LateInitializationError`.

Комментарий в коде утверждает обратное: «debugNeedsPaint is a real getter in release builds». Это неверно.

`_captureOutgoing()` вызывается синхронно из `_onTapTab()` **до** `context.go(...)`. Исключение в обработчике тапа обрывает колбэк → `context.go` не выполняется → таб не переключается. В debug всё работает, `dart analyze` молчит, тесты зелёные. Ломается только собранный APK.

Фикс: убрать проверку или перенести её внутрь `try`, обернув в `kDebugMode`.

## Производительность и лаги

### ЛАГ-7. Почему настройки лагают — полная цепочка

`settings_appearance_screen.dart`, `_SliderSettingTile`:

```dart
onChangeEnd: (_) { setState(() => _isDragging = false); },   // только флаг
onChanged: (double v) {
  if (v != widget.value) {
    HapticService.selection();          // хаптик на КАЖДЫЙ тик
    widget.onChanged(v);                // → setUiCornerRadius(v)
  }
},
```

Дальше по цепочке на каждый тик слайдера:

1. `uiCornerRadius` входит в `VisualThemeSettings` → меняется ключ кэша темы;
2. `AppTheme.themed()` строит новый `ThemeData` + `ColorScheme.fromSeed(...)` — и **дважды**, потому что `main.dart` вызывает его для `theme:` и `darkTheme:`;
3. `_appearanceThemeProvider` строит **третий** `ThemeData` для этого экрана;
4. всё это завёрнуто в `AnimatedTheme(duration: 350ms, curve: expressiveStandard)` → каждый тик **перезапускает** полный `ThemeData.lerp` по ~40 сабтемам, который крутится 350 мс на 60 fps;
5. `_AppearanceScreen` делает `ref.watch(uiSettingsProvider)` целиком → перестраивается весь экран вместе с mesh-баннером;
6. `ProfileScreen` под ним тоже watch'ит `uiSettingsProvider` целиком (ПРФ-1) → перестраивается 75 KB экрана;
7. `HapticService.selection()` дёргает platform channel и вибромотор 20 раз за один жест.

Фикс: `onChanged` пишет только в локальный `ValueNotifier` (бейдж + позиция ползунка), коммит в нотифаер — в `onChangeEnd`; хаптик по смене division, а не по тику; `AnimatedTheme` отключать на время drag; везде `.select`.

**ЛАГ-8. Кэш темы гарантированно промахивается.** Слайдер `uiCornerRadius`: `min 8, max 28, divisions 20` = 21 дискретное значение. Кэш в `app_theme.dart` — ровно 20 записей с вытеснением `while (length > 20) remove(keys.first)`, то есть FIFO, а не LRU. Один проход слайдера по всему диапазону вытесняет весь кэш, обратный проход — 100 % промахов.

**ЛАГ-9. `main.dart` пересобирает всё приложение на каждый кадр анимации клавиатуры.**

```dart

  final mediaQuery = MediaQuery.of(context).copyWith(
    textScaler: TextScaler.linear(fontScale.scale),
```

`MediaQuery.of(context)` подписывает `builder` на **любое** изменение `MediaQueryData`, включая `viewInsets`. Открытие клавиатуры в чате → десятки кадров, на каждом пересобирается поддерево роутера и три оверлея (`IncomingCallOverlay`, `CallOverlay`, `InAppNotificationBannerOverlay`). **ЛАГ-10. Сайд-эффект в `build()`.** `AppTimeSettings.configure(...)` вызывается прямо в `PulseApp.build()` — прямое нарушение правила 6 протокола («No Side-Effects in build()»). **ЛАГ-12. Анимация смены темы сделана самым дорогим способом.** `circular_theme_reveal.dart`: `await boundary.toImage(pixelRatio: 1.0)` — асинхронное чтение GPU→CPU всего экрана (правило 1 протокола требует `toImageSync`). На экране, который и без того пересобирает тему на каждый тик.

**ЛАГ-14. Крупные `ref.watch` без `select`.** `ProfileScreen.build`: `ref.watch(authProvider)` + `ref.watch(uiSettingsProvider)` целиком. `_AppearanceScreen`: `ref.watch(uiSettingsProvider)` целиком. ## Цвета и тема

### ЦВЕТ-7. Ключ кэша темы собран через XOR — это ломает тёмную тему

```dart
final int cacheKey = settings.seedColor.toARGB32()
    ^ brightness.index                                  // бит 0
    ^ (settings.themeMode.index << 8)                   // биты 8–9
    ^ (settings.useSystemDynamic ? 1 : 0)               // ТОЖЕ бит 0
    ^ (settings.predictiveBackEnabled ? ((settings.predictiveBackStrength * 100).round() << 4) : 0)
    ^ (settings.pureBlackOled ? 4 : 0)
    ^ (settings.uiCornerRadius.round() << 12)
    ^ (settings.paletteStyle.index << 18)
    ^ ((contrastLevel * 100).round() << 21)
    ^ (dynamicScheme?.primary.toARGB32() ?? 0);
```

Конкретные коллизии:

- `brightness.index` и `useSystemDynamic` занимают **один и тот же бит 0**. Когда `dynamicScheme == null` для обеих яркостей (десктоп, web, Android до 12, либо первые кадры до прихода Monet), ключ светлой темы при выключенных системных цветах **совпадает** с ключом тёмной темы при включённых. Включаешь «Системные цвета» в тёмной теме — получаешь из кэша готовую **светлую** `ThemeData`. Светлые поверхности в тёмной теме.
- `(strength * 100).round() << 4` при strength 0.5…1.5 даёт 50…150, то есть биты 4–11, и **перекрывает** `themeMode.index << 8`.
- `(contrastLevel * 100).round() << 21` при высоком контрасте даёт `100 << 21`, биты 21–27, и налезает на альфа-байт `seedColor.toARGB32()` (биты 24–31).
- Если пользователь выбрал seed, равный `dynamicScheme.primary` (типичный случай — взял цвет из системной палитры), два 32-битных слагаемых XOR'ятся в **ноль** и оба исчезают из ключа.

Фикс — один вызов:

```dart
final int cacheKey = Object.hash(
  settings.seedColor.toARGB32(), brightness.index, settings.themeMode.index,
  settings.useSystemDynamic, settings.predictiveBackEnabled,
  settings.predictiveBackStrength, settings.pureBlackOled,
  settings.uiCornerRadius, settings.paletteStyle.index,
  contrastLevel, dynamicScheme?.primary.toARGB32(),
);
```

И вытеснение переделать в LRU (при попадании — `remove` + `[key] =`), иначе ЛАГ-8 остаётся.

**ЦВЕТ-8. При включённых системных цветах половина настроек мертва.**

```dart
final ColorScheme baseScheme = (settings.useSystemDynamic && dynamicScheme != null)
```

**ЦВЕТ-12. `avatarColorFor` продублирован дословно и не зависит от палитры.** `app_colors.dart` целиком:


**ПРФ-9. `MyQrCodeSheet` нарушает дизайн-правила.** `boxShadow` (запрещён), `BorderRadius.circular(28)` и `(16)` вместо токенов, и статический `show()`, дублирующий прямой вызов `AppBottomSheets.show`.

## Звонки

**ЗВН-1** — см. РОУТ-1, это главный блокер этого раздела.

**ЗВН-2. Бесконечная крутилка как штатное состояние.** `ActiveCallScreen` при `session == null` показывает `AppLoadingIndicator` без таймаута и без retry. Любая гонка (push пришёл раньше, чем выставилась сессия; восстановление маршрута; РОУТ-1) = мёртвый экран с одной кнопкой «назад».

**ЗВН-3. `ref.read` в `dispose`.** `ActiveCallScreen.dispose()` вызывает `ref.read(isCallScreenOpenProvider.notifier).setOpen(false)`. В Riverpod 3 это небезопасно при сносе контейнера, а при несовпадающем порядке mount/unmount двух экземпляров флаг рассинхронизируется.

**ЗВН-4. Разрешения запрашиваются дважды.** `OutgoingCallScreen._startCallFlow()` вызывает `PermissionService().requestCallPermissions(video:)`, затем `call_starter.startOutgoingCall()` вызывает его же. Правильное место — `call_starter`, из экрана убрать.

**ЗВН-5. Отказ в разрешениях молча превращается в режим слушателя.** `if (!perm) { isListener = true; }` в обоих `startOutgoingCall` и `startIncomingCall`. Пользователь получает звонок без микрофона, а уведомление об этом живёт 3 кадра до `pushReplacement`. Плюс `..start(preferQuic: false)` захардкожено, хотя `quic_transport.dart` в проекте есть.

**ЗВН-6. Непроверенный каст серверного JSON.**

```dart
final int callId = ((result['payload']?['message_id']
    ?? result['message_id'] ?? initResult.callId) as num).toInt();
```

Если все три `null` — сырой `TypeError` посреди запуска звонка, без пользовательского сообщения.

**ЗВН-7. Три разных правила «это бот».** В `call_starter`: `chat.isBotChat || peerName.endsWith('_bot') || chat.username.endsWith('_bot')`. В `OutgoingCallScreen`: `endsWith('_bot') || == 'bot'`. В публичном профиле — своя проверка. Нужен один хелпер.

## Архитектура и мусор

**АРХ-1. `AppHeights` объявлен и не используется нигде.** Вместо него по экранам разбросаны `Size.fromHeight(48)`, `Size.fromHeight(44)`, `Size(60, 36)`, `SizedBox(height: 38)`, `SizedBox(height: 56)`, `SizedBox(height: 34/18)`. При этом `minimumSize` из темы кнопок удалили ради теста. Как следствие — кнопки быстрых действий в профиле имеют высоту **38 dp**, ниже минимума 48 dp по M3 и по доступности.

**АРХ-2. Две параллельные системы радиусов.** Статический `AppRadii.mdRadius` (не реагирует на настройку скругления) и реактивный `AppRadii.of(context)` через `AppRadiiTheme`. `profile_screen` использует статический, `_ThemeModeSelectorCard` — реактивный. Итог: слайдер «Скругление интерфейса» меняет часть углов и не меняет другую. Плюс десятки сырых `BorderRadius.circular(10/12/16/18/20/24/26/28)` в прочитанных файлах.

**АРХ-3. Брейкпоинты дублируются.** `Breakpoints.medium = 840` есть, но `settings_appearance_screen` пишет `840` числом, а ширины ограничены хардкодом `780`, `820`, `860`, `1120`, `480`, `360`, `340`, `260`, `640`.

**АРХ-4. Мёртвый и дублирующийся код в провайдерах.** `chat_muted_provider.dart` (1 084 B) не используется. `providers/adaptive_performance_provider.dart` — 159-байтный реэкспорт, реальный лежит в `core/performance/` → два пути импорта одного провайдера. `favorite_contacts_service.dart` по-прежнему только пишет (чтение `favoriteContactsProvider` не подтверждено — нужен grep-гейт).

**АРХ-5. Дублирующиеся имена навигации.** Модульный `openDirectChat(...)` в `direct_chat_navigator.dart` конфликтует по смыслу с `ChatRepository.openDirectChat(...)`; `ChatRedirectScreen` фактически мёртв (РОУТ-5).

**АРХ-6. Три оверлея живут внутри `MaterialApp.builder`.** `IncomingCallOverlay`, `CallOverlay`, `InAppNotificationBannerOverlay` пересобираются вместе с `builder`, то есть на каждое изменение темы/настроек и на каждый кадр клавиатуры (ЛАГ-9).

**АРХ-7. `DynamicColorBuilder` создаётся дважды.** Один раз в `main.dart` вокруг всего приложения, второй — внутри `_AppearanceScreen`. Дубль платформенного запроса и два источника истины для системной схемы.

**АРХ-8. У сплэша нет таймаута.** `_startFlow()` ждёт `Future.wait([sessionProvider.ensureLoaded(), authProvider.ensureLoaded()])`, а `AuthNotifier._load()` внутри себя `await refreshProfile()` (сетевой `getMe`). Ни одного таймаута. На мёртвой сети сплэш висит бесконечно, индикатор появляется только через 500 мс, `catch (_)` глотает причину и показывает общий `splashInitError`.

**АРХ-9. Тестовый хук в продакшене.** `AuthNotifier._load()` на web на каждом холодном старте делает `http.get('/mock_reset.json').timeout(2s)`. Файла в прод-сборке нет → до 2 секунд впустую на критическом пути загрузки, ошибка проглочена `catch (_)`.

**АРХ-10. Четыре несвязанных отложенных футуры на первом кадре шелла.** `_checkBiometricLock` (500 мс), `_showAlphaDialog` (800 мс), `_checkWebPushPrompt` (1500 мс), `_checkDailyOtaUpdate` (3000 мс) — ни одна не отменяется в `dispose`, и alpha-диалог, биометрия и OTA-диалог могут наложиться друг на друга.

**АРХ-11. Двойной выход из приложения.** `_checkBiometricLock` при неудачной аутентификации вызывает `SystemUtils.minimizeApp()`, а затем ещё и `SystemNavigator.pop()`.

**АРХ-12. `_lastBackPressTime` не сбрасывается при смене таба.** «Нажмите ещё раз для выхода» может сработать на второй back после возврата с другого таба.
