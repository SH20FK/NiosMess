## Главный вывод

Экран «Резолвим @username» показывается, чтобы получить число, которое **уже лежит в стейте того же виджета, с которого ты нажал кнопку**. Это не медленная сеть — это три лишних сетевых круга и один лишний экран в стеке.

### Трассировка «открыл профиль → нажал Написать»

1. `initState` → `_checkCacheAndLoad()`. Профиль есть в кэше → сразу `_resolveChatId(cached)`.
2. `_resolveChatId` ищет диалог в `chatsProvider`; не нашёл → `chatRepository.openDirectChatByUsername(...)` → WS `open_direct` → `_resolvedChatId = result.chatId`. **Диалог создан, id в стейте.**
3. Тот же `_checkCacheAndLoad` затем безусловно вызывает `_loadProfile()`, который при успехе снова вызывает `_resolveChatId(profile)` → **второй `open_direct` по тому же юзеру, параллельно с первым**.
4. Жмёшь «Написать» → `context.push('/chat/dm/' + username)`. Кнопка **даже не смотрит** на `_resolvedChatId` — это поле используется только для `ProfileSharedMediaTabView(chatId: _resolvedChatId)`.
5. `DirectChatResolverScreen` открывается на весь экран, `addPostFrameCallback` → `_resolve()` → **третий `open_direct`**.
6. Дальше `await ref.read(chatsProvider.notifier).refresh()` — полный `list_chats` по вебсокету, самый тяжёлый запрос в приложении, **на критическом пути до навигации**.
7. И только потом `context.go('/chat/' + id)`.

Именно шаг 6 и даёт основную задержку, которую ты видишь. `open_direct` быстрый, `list_chats` — нет.

### Побочный эффект: просмотр профиля создаёт диалог

`open_direct` — это create-or-get (см. `ChatRepository.openDirectChat`). Значит **само открытие чужого профиля уже создаёт с ним директ**, дважды. Полистал поиск, зашёл в три профиля — получил три диалога. Причём это срабатывает даже если пользователь тебя заблокировал: `_resolveChatId` отстреливает из `initState`, а баннер блокировки рисуется потом. Проверь на сервере, персистится ли пустой диалог и виден ли он собеседнику — если да, это утечка активности («я заходил на твой профиль»).

### Заодно ломается стек навигации

Профиль делает `push`, резолвер делает `go('/chat/' + id)`. `go` перестраивает стек от корня маршрута, то есть профиль из стека **исчезает**. Назад из чата ты попадаешь не в профиль, откуда пришёл, а туда, куда решит роутер. Для звонка то же самое.

## 2. Звонок: та же болезнь плюс разрешения

`context.push('/call/dm/' + username + '?isVideo=0')` → `CallRedirectScreen`:

1. `openDirectChatByUsername` — **ещё один** `open_direct`, хотя id уже есть в профиле.
2. `await chatsProvider.refresh()` — снова полный `list_chats`.
3. `startOutgoingCall(...)`, а внутри `PermissionService().requestCallPermissions(video:)` — **системный диалог разрешений поверх страницы загрузки**.
4. `callRepository.initiate` → создание SFU-комнаты → `deriveCallMediaKey` (ECDH по ключу партнёра) → `CallSessionManager.start(preferQuic: false)`.
5. `context.go('/call/' + callId)`.

Три сетевых раунда и криптография до того, как ты увидишь что-то похожее на звонок. В эталонных мессенджерах экран звонка открывается **мгновенно** в состоянии «Соединение…» — аватар, имя, кнопка отмены — а вся эта работа идёт под ним. Здесь наоборот: абстрактный спиннер, потом резкий перескок в звонок.

Два реальных бага в этой же цепочке:

- **Тихий listener-режим.** Если разрешения не выданы, `startOutgoingCall` ставит `isListener = true` и звонит дальше. Пользователь уходит в звонок без микрофона и **без единого слова в интерфейсе**.
- **Сырое исключение в UI.** `on CallStartException` в `CallRedirectScreen` разбирает только `CallStartFailure.permissions`. Второй вариант, `botForbidden`, падает в `chatCallFailed(error)`, и пользователь видит текст `CallStartException(CallStartFailure.botForbidden)`. Там же во всех трёх резолверах `_error = error is ApiException ? error.message : '$error'` — то есть `toString()` дартового исключения прямо на экране.

## 3. Целевая архитектура: навигация без интерстишлов

Один helper вместо трёх экранов. Принцип: **синхронный путь, если id известен; оптимистичная навигация, если нет.**

```
// lib/core/navigation/direct_chat_navigator.dart

/// Открывает директ мгновенно, если id уже известен, и оптимистично —
/// если нет. Никогда не показывает отдельный экран ожидания.
Future<void> openDirectChat(
  BuildContext context,
  WidgetRef ref, {
  required String username,
  int? userId,
  int? knownChatId,
  bool isSecret = false,
}) async {
  // 1. Быстрый путь: id уже есть (из профиля) или чат есть в списке.
  final int? fast = knownChatId ??
      ref.read(chatsProvider).value?.firstWhereOrNull((c) =>
          c.chatType == 'direct' &&
          c.username?.toLowerCase() == username.toLowerCase())?.id;

  if (fast != null && fast > 0 && !isSecret) {
    context.push('/chat/$fast');
    return;
  }

  // 2. Медленный путь: открываем чат сразу, с известным именем и аватаром.
  //    ChatDetailScreen сам дожидается chatId и показывает шиммер в списке
  //    сообщений, а не пустой экран с надписью.
  context.push(
    '/chat/pending',
    extra: PendingChat(username: username, userId: userId, isSecret: isSecret),
  );
}
```

Что меняется на практике:

- **`_resolvedChatId` начинает использоваться.** Кнопки профиля передают его в `knownChatId`. В 95 % случаев переход становится синхронным — ноль сети, ноль спиннеров.
- **`refresh()` уходит с горячего пути.** `upsertChat(syntheticChat)` из резолвера уже кладёт чат в локальный стейт; полный `list_chats` вызывается **после** навигации, без `await`.
- **`push` вместо `go`.** Стек сохраняется, назад из чата возвращает в профиль.
- **Секретный чат — единственный честно медленный путь** (`e2ee.getPublicKeyBase64()` + `setPublicKey` + `open_direct` с ключом). Но и он не заслуживает отдельного экрана: прогресс живёт внутри кнопки, а затем открывается чат с плашкой «Устанавливаю шифрование».
- **`/chat/dm/:username` остаётся только как вход для диплинков** (внешняя ссылка, контекста нет). Внутри приложения этот маршрут не используется никогда.

Состояние кнопки вместо экрана:

```
// idle → иконка; pending → 18px индикатор внутри той же фигуры;
// error → error-тинт и повторный тап
enum ActionPhase { idle, pending, error }
```

Звонок:

```
// Вместо /call/dm/:username → сразу экран звонка в состоянии connecting.
context.push('/call/outgoing', extra: OutgoingCallArgs(
  username: profile.username,
  displayName: profile.displayName,
  avatarUrl: profile.avatarUrl,
  chatId: _resolvedChatId,        // может быть null — экран дорезолвит сам
  isVideo: isVideo,
));
```

Экран звонка рисует аватар, имя и «Соединение…», а `resolve → permissions → initiate → SFU` крутится под ним. Разрешения запрашиваются **там**, с нормальным объяснением, и при отказе показывается явное «Микрофон недоступен — вы подключитесь как слушатель» с выбором, а не молча.

## 4. Экран профиля: структура

### Фальшивый баннер на магических числах

Hero-шапка собрана так: `Stack` с `SizedBox(height: 100)` («header top spacing»), внутри `Positioned(bottom: -54)` с аватаром радиуса 54 и рамкой 4, снаружи компенсирующий `SizedBox(height: 62)`. Плюс `extendBodyBehindAppBar: true` и прозрачный `AppBar`.

Итого: **верхние 100 px — пустая `surface`**, отведённая под баннер, которого не существует. Аватар вылезает за границы родителя отрицательным отступом, и высота держится четырьмя несвязанными константами (100 / −54 / 62 / 54+4). Изменится высота статус-бара или аватара — вёрстка разъедется. И визуально это именно то, что ты видишь как «неоч»: сверху дыра, потом внезапно аватар.

Два честных варианта:

1. **Сделать баннер настоящим.** Градиент из доминирующего цвета аватара (или обложка профиля, если завести её на бэкенде), высота 140–160, аватар наезжает на него снизу. Тогда 100 px перестают быть пустотой.
2. **Убрать баннер и взять коллапсящуюся шапку.** В репозитории **уже есть** `lib/widgets/profile_header_delegate.dart` (`ProfileHeaderDelegate`, `minExtent 68`, `maxExtent 220`, готовые `expandedOpacity`/`collapsedOpacity`, аватар 76 → 36). Он написан ровно под это и здесь не используется. Профиль переезжает на `CustomScrollView` + `SliverPersistentHeader`, и при скролле имя уезжает в `AppBar` — как в Telegram.

Второй вариант предпочтительнее: он же решает следующую проблему.

### Вложенные скроллы

Весь профиль — это `SingleChildScrollView`, в конце которого лежит `ProfileSharedMediaTabView` (48 834 байт, вкладки с медиа). Табы с собственными списками внутри нескроллируемого по высоте родителя — это либо вложенный скролл, либо `shrinkWrap`, то есть прямое нарушение правил 7 и 2 вашего `AGENTS.md`. Всё содержимое строится жадно, ни одного слайвера. Правильно: `CustomScrollView` → `SliverPersistentHeader` (шапка) → `SliverToBoxAdapter` (действия, инфо) → `SliverFillRemaining` с `TabBarView`, либо `NestedScrollView`.

### Прозрачный AppBar без подложки

`scrolledUnderElevation: 0`, `backgroundColor: Colors.transparent`, `extendBodyBehindAppBar: true` — и никакого скрима. Кнопки спасает только `IconButton.filledTonal` с `surfaceContainerHigh α0.7`, то есть полупрозрачная плашка поверх непредсказуемого фона. Как только под ней проедет аватар или баннер, контраст поедет. Нужен либо `flexibleSpace` с градиентным скримом, либо `scrolledUnderElevation` по умолчанию с нормальным `surfaceContainer` при скролле.

### `isMe` — тупик

Если это твой профиль, `if (!isMe)` вырезает и док действий, и меню в правом верхнем углу, и баннер блокировки. Остаётся аватар, имя и карточка «только чтение» **без единой кнопки**. Ни «Редактировать», ни перехода в `/main/profile`. Вероятно, сюда вообще не должно быть входа для себя: при `isMe` — редирект на свою вкладку профиля.

## 5. Действия: четыре равных вместо иерархии

`_buildQuickActionDock` — `Row` из четырёх `Expanded` с `_QuickActionButton`: Написать, Позвонить, Видео, Секретный чат. Все четыре — одна и та же `M3Container(Shapes.c9_sided_cookie, 48×48)` с `color.withValues(alpha: 0.15)`. Одинаковый вес, одинаковая форма, разный только оттенок.

Проблемы:

- **Нет главного действия.** В мессенджере первичное действие — «Написать». Оно должно быть широкой `FilledButton`, а звонок/видео — вторичными, а секретный чат — вообще в меню «⋮», где ему и место по частоте использования.
- **`color.withValues(alpha: 0.15)`** — это ручной тинт мимо схемы. Есть `primaryContainer`, `secondaryContainer`, `tertiaryContainer` ровно для этого. Альфа поверх `surface` даёт цвет, которого нет ни в одном токене.
- **Лейбл в `SizedBox(height: 28)`** с `labelSmall`, `fontSize: 11`, `height: 1.15`, `maxLines: 2`, `letterSpacing: -0.2`. При `AppFontScale 1.3` или длинном переводе («Секретный чат», англ. «Secret chat») текст обрезается по высоте контейнера, а не по `ellipsis`. Фиксированную высоту надо убрать.
- **Неверный l10n-ключ.** Подпись секретного чата — `context.l10n.settingsSecretChatsButton`, то есть ключ из **настроек**. Строка написана под строку настроек, а стоит в профиле.
- **Док утоплен в тень и рамку одновременно:** `surfaceContainerHigh α0.65` + `outlineVariant α0.18` + `BoxShadow(α0.04, blur 16)`. По вашему же протоколу `BoxShadow` запрещён, глубина — тоном. И альфа на контейнерном токене снова даёт непонятный промежуточный цвет.
- **`.animate().fade().slideY()`** висит на `Container` в `build` без ключа — при каждом `setState` (а их тут много: блок, разблок, резолв id) анимация перезапускается и док мигает.

## 6. Чего на профиле нет вообще

Это не придирки к вёрстке, это отсутствующая функциональность:

- **Онлайн-статус / «был(а) в сети»** — самый ожидаемый элемент профиля в мессенджере. Его нет ни в шапке, ни в карточке.
- **Уведомления / mute для этого диалога** — нет.
- **Общие группы** — нет.
- **Поиск по переписке** — нет.
- **Поделиться профилем / QR** — нет, хотя `lib/widgets/profile/my_qr_code_sheet.dart` уже написан для своего профиля.
- **Добавить в контакты** — нет, при том что экран `contacts_screen.dart` на 45 КБ существует.
- **Медиа/Файлы/Ссылки/Голосовые** — `ProfileSharedMediaTabView` есть, но он получает `chatId` и при `null` не покажет ничего; при провале резолва получит `-1`.

Меню «⋮» сейчас содержит ровно два пункта: блок и жалоба. Для чужого профиля этого мало.

## 7. Локализация: экран написан по-русски в коде

Прямое нарушение правила «все строки через `context.l10n.key`». Захардкожено в `public_profile_screen.dart`:

`'О себе'`, `'Имя пользователя'`, `'Регистрация'`, `'Телефон'`, `'День рождения'`, `'Имя пользователя скопировано'`, `'Номер телефона скопирован'`, `'Не удалось получить данные с сервера'`, `'Пользователь заблокирован вами'`, `'Пользователь ограничил доступ'`, `'Вы не можете обмениваться сообщениями и совершать звонки'`, `'Вы добавлены в чёрный список этого пользователя'`.

Плюс две вещи хуже, чем просто хардкод:

- **Ручное ветвление локали.** `final bool isRu = context.l10n.localeName.startsWith('ru');` и дальше два текста ошибки на двух языках прямо в `catch`. Это ровно то, для чего существует ARB.
- **`DateFormat('d MMMM yyyy', 'ru')`** — дата регистрации всегда на русском, независимо от языка приложения. В английской локали получишь «15 сентября 2026».

В `direct_chat_resolver_screen.dart` — `Colors.green` для иконки замка, мимо `ColorScheme` и мимо правила «никаких literal-цветов».

## 8. Баги

- **Инвизибл-рипплы.** `_buildInfoRow` возвращает `InkWell` **внутри** `Container` с `BoxDecoration` (`_buildAboutCard`). Ближайший `Material` находится под декорацией, поэтому всплеск краски рисуется **за** фоном карточки и его не видно. Строки «скопировать имя» и «скопировать телефон» нажимаются без визуального отклика. Нужен `Material` внутри карточки (или `Ink` вместо `Container`).
- **Двойной `open_direct` при открытии профиля** (см. §1, шаги 2–3).
- **`-1` как sentinel.** `_resolvedChatId = -1` означает «не удалось», и это значение **улетает в дочерний виджет** `ProfileSharedMediaTabView(chatId: -1)`. Нужен явный тип состояния, а не магическое число в `int?`.
- **Мёртвая ветка ошибки в `chat_redirect_screen.dart`.** `_loading` выставляется в `true` и **никогда** не сбрасывается; `_error` не присваивается нигде (в `catch` вместо этого делается `context.go`). Значит весь блок `else` в `build` (иконка `link_off`, текст, кнопка «Назад») — **недостижимый код**.
- **Контраст на деструктивной кнопке.** В `_showBlockDialog` — `FilledButton.styleFrom(backgroundColor: scheme.error)` **без** `foregroundColor: scheme.onError`. Текст остаётся `onPrimary` на фоне `error`.
- **Проверка support после подтверждения.** «Support нельзя заблокировать» проверяется **внутри** обработчика, уже после `Navigator.pop()`. Пользователь проходит весь диалог подтверждения и только потом получает отказ. Пункт нужно скрывать заранее.
- **Порядок кнопок.** Во всех трёх шитах подтверждающая кнопка слева, «Отмена» справа — обратно платформенной конвенции.
- **Пустой `setState(() {})`** после блокировки и разблокировки. Состояние блокировки и так читается через `ref.watch(privacyProvider)` в `Builder`. Зато `profile.isBlockedByMe`, который участвует в том же `||`, никогда не обновляется и остаётся устаревшим до перезагрузки профиля.
- **`_error` не показывается, если профиль уже есть.** Если фоновое обновление упало, ты видишь кэш без всякого признака, что данные старые.
- **Присваивание полей вне `setState`.** `_profile = cached;` и `_resolvedChatId = c.id;` в `_checkCacheAndLoad` — работает только потому, что метод вызывается из `initState` либо после внешнего `setState`. Хрупко.
- **Жалоба с `chatId: 0`.** `_submitUserReport` шлёт `chatId: 0` как заглушку — ещё один sentinel.
- **`BouncingScrollPhysics` захардкожен** — iOS-физика на Android.
- **`contact_detail_screen.dart`** — `ConsumerStatefulWidget` без состояния, чей `build` возвращает `PublicProfileScreen`. Файл на 614 байт, который должен быть алиасом маршрута.

## 9. Прилегающее: диплинк `/u/` ведёт не туда

`ChatRedirectScreen._resolve()` для слага без `+`:

1. `chatRepository.resolveShortLink(cleanSlug)` → WS `get_invite_info`. То есть **ссылка на пользователя резолвится через эндпоинт приглашений в чат**.
2. Если сервер вернул `slug`, результат — `'/join?slug=...'`, и пользовательская ссылка уезжает на экран присоединения к чату.
3. Если не вернул ничего или упал — `context.go('/chat/dm/' + cleanSlug)`, то есть **сразу создаётся диалог**.

По ссылке вида `ni-os.ru/u/someone` человек должен попадать на **профиль**, а не в созданный на лету пустой чат и не в «присоединиться». Правильная цепочка: `/u/:slug` → пробуем как приглашение только если слаг начинается с `+`, иначе → `/profile/:username`, откуда пользователь сам решает, писать ему или нет. Это же убирает создание диалогов по чужим ссылкам.

### Три почти одинаковых экрана-заглушки

`direct_chat_resolver_screen`, `call_redirect_screen`, `chat_redirect_screen` — один и тот же паттерн, скопированный трижды: `PulseScaffoldBody(maxWidth: 560)`, `AnimatedSwitcher(220 ms)`, `AppLoadingIndicator(size: 64)`, иконка 48/56, ряд «Назад + Повторить». Около 500 строк интерстишл-UI, правильный ответ для которого — «его не должно быть». После §3 остаётся максимум один тонкий диплинк-резолвер без собственного экрана.

### Мелочи по API

`openDirectChatByUsername(username)` — чистый проброс в `openDirectChat(username:)`, который **не передаёт `userId`**. Две функции на одно действие; вторая существует только ради более короткого вызова. Оставить одну.

## 10. Токены

## 12. Критерии приёмки

1. Открытие профиля не отправляет ни одного `open_direct`. Проверяется логом вебсокета.
2. «Написать» при существующем диалоге открывает чат **в том же кадре**, без сетевых запросов, без промежуточного экрана.
3. «Написать» при отсутствующем диалоге открывает экран чата немедленно: шапка с именем и аватаром известна сразу, список сообщений — шиммер. Отдельного экрана ожидания нет.
4. «Позвонить» открывает экран звонка немедленно в состоянии «Соединение…»; разрешения запрашиваются на этом экране, а при отказе явно показано, что подключение будет в режиме слушателя.
5. Назад из чата и из звонка возвращает **в профиль**, откуда пришёл.
6. `list_chats` не вызывается на пути к открытию чата или звонка (проверяется логом).
7. Пользователь никогда не видит `toString()` дартового исключения; `botForbidden` имеет собственный текст.
8. В `lib/screens/public_profile_screen.dart` нет русских строк вне ARB; дата регистрации форматируется по текущей локали.
9. Все тапабельные строки имеют видимый ripple (ручная проверка карточки «о себе»).
10. Профиль скроллится одним слайвер-скроллом; `ProfileSharedMediaTabView` не вложен в `SingleChildScrollView`.
11. На экране не более четырёх радиусов и трёх размеров иконок, ни одного `BoxShadow`.
12. Подписи быстрых действий не обрезаются при ширине 320 dp и масштабе шрифта 1.3.
13. Ссылка `/u/:username` открывает профиль, а не чат и не экран присоединения.
14. `flutter analyze` — ноль, `dart test` зелёный.
